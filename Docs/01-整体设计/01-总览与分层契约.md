# 01 总览与分层契约

> 定位：整套架构的地基卷。先定**分层、依赖方向、跨卷契约**与**"不针对机制"的扩展模型**，其余卷都服从本卷约束。
> 关联：`03`（时机）是贯穿所有层的连接件；本卷只讲边界，不重复各卷细节。

## 1. 核心命题

> **回合流程是同步的状态机；技能干预点是异步的响应窗口；结算行为是生命周期完整的交易对象；机制是数据的组合而非引擎的分支。**

四条承诺贯穿全体系：

| 承诺 | 含义 |
|---|---|
| 服务器权威 | 一切规则裁决只在服务器发生。客户端只消费复制结果、事实通知与演出。 |
| 事件二分 | 事实通知（已发生、不可否决）同步多播；时机查询（将发生、可被干预）走异步响应窗口。两通道绝不混用。 |
| 结算交易化 | 伤害、移牌、濒死等"会发生事"不是函数调用，而是有生命周期的交易对象。交易不依赖栈帧存活——它就是悬停点本身。 |
| 规则与表现分离 | 服务器规则层不等待动画。客户端异步由表现队列消化，永不反向影响规则。 |

## 2. 分层模型

```
┌─────────────────────────────────────────────────────────────┐
│  表现层（客户端）            —— 复制/通知/GameplayCue 驱动     │
├─────────────────────────────────────────────────────────────┤
│  交互层（服务器）            —— 响应窗口 / 选择输入校验          │  卷10、11
├─────────────────────────────────────────────────────────────┤
│  规则层（服务器）            —— 回合 FSM + 时机总线 + 交易引擎   │  卷02、03、04
├─────────────────────────────────────────────────────────────┤
│  语义层（服务器，无状态裁决）  —— 目标/距离/频率/效果 的纯裁决     │  卷05、06、07
├─────────────────────────────────────────────────────────────┤
│  数据层（注册表/声明）        —— 卡/技/效果 声明与标签            │  卷08、09
└─────────────────────────────────────────────────────────────┘
```

关键阅读：**层只允许依赖自己下方一层及接口层**。规则层绝不写死任何卡牌或技能名；语义层全部由纯函数/可注入规则构成；数据层只为声明提供数据，不含行为。

## 3. 依赖方向（谁可以引用谁）

| 依赖方 | 可依赖 | 绝不依赖 |
|---|---|---|
| 规则层（流程/时机/交易） | 语义层接口、数据层声明、标签 | 具体卡牌技能体、表现细节 |
| 语义层（目标/频率/效果裁决） | 数据声明、标签、对象接口 | 流程顺序、窗口实现、复制 |
| 交互层（窗口/输入） | 规则层开放的口、技能体激活 | 具体某张牌的判定逻辑 |
| 表现层（客户端） | 复制属性、通知委托、Cue | 任何规则决策 |

落地即代码依赖规约：
- 引擎模块可 `include` 类型/标签头，**不可 `include` 具体卡牌或具体技能**的实现文件；新机制必须放在"内容/数据"侧。
- 容器接口、目标校验器、频率账本等一律接口化，依赖注入，不允许引擎侧分支 `if(卡名)`。

## 4. 跨卷契约（本卷只登记，细则在各卷）

| 契约 | 内容 | 约束出处 |
|---|---|---|
| 时机标签表 | 事实通知、查询时机、窗口策略由谁开、谁听 | `03` |
| 交易协议 | 交易四态；窗口关闭统一收敛到 `Finish/Cancel` | `04` |
| 目标裁决协议 | 合法目标 = 数据声明 × 语义校验器 × 现场状态；距离由 Provider 注入 | `05` |
| 状态协议 | 状态只由"带来源的修改"产生；到期/层数由自身生命周期管 | `06` |
| 频率账本协议 | 计数键命名空间；上限、复用、重置的统一入口 | `07` |
| 区域协议 | 区域 Tag → 容器的单一解析入口；跨区一律经交易 | `08` |
| 技能协议 | 触发 = 时机索引命中 + 询问/自动；修改技=演化副本 | `09` |
| 响应协议 | 窗口策略（全体/按序/首个）+ 优先级 + 超时 + 锁 | `10` |
| 权威协议 | 所有改状态的入口都有 `IsRunningOnServer()` 门控 | `11` |

## 6. "不针对机制"的扩展模型（本卷最重要的方法论）

### 6.1 引擎只有七种抽象形状

所有能想到的机制，最终都落到以下七种**形状**的组合里。引擎只实现形状，不实现机制：

| # | 形状 | 例子（只是样本，不是框架） |
|---|---|---|
| 1 | 阶段/时机标签 | "进入判定阶段前"、"受到伤害时" |
| 2 | 交易（带查询时机） | 移动、伤害、濒死、弃置 |
| 3 | 目标集 + 校验器 | 距离、花色、身份限制 |
| 4 | 频率账本 | 每回合一次、整局两次、修改后 +1 |
| 5 | 状态/效果（带来源与到期） | BUFF、标记、持续到回合结束 |
| 6 | 响应链（窗口策略嵌套） | 抵消、要求出牌回应 |
| 7 | 技能声明 → 技能体 | 任意角色的任意技能 = 此形状的实例 |

### 6.2 新增机制的固定五步（写进文档总览，全体系遵守）

1. 挑**形状**：看机制由哪几种形状组合；
2. 注册**标签**：给新时机/区域/效果命名（原生 GameplayTag 或数据资产）；
3. 写**数据**：技能声明（监听时机、激活类型、优先级、次数上限、目标规则）；
4. 实现**技能体**：仅在技能体内组合形状（AbilityTask 串联、调交易、调账本）；
5. 放**案例**：把该机制整理进相关卷的「案例」小节。

若五步中出现"需要改引擎/流程代码才能做"，说明抽象形状缺失或耦合了——应立即回写本卷评审，而不是打补丁。

### 6.3 反例与正例

- ✗ 引擎认识 `HeartGuard`、`无懈`、`流离`，窗口为它特判。
- ✓ 引擎开 `Event.Timing.Damage.Incoming` 窗口、按目标名单顺序询问；"红桃判定无视伤害"是挂在该时机下的一个普通技能实例。

## 7. 变更与评审纪律

- 任何影响跨卷契约的改动（新增形状、改窗口语义、改交易协议）都必须回到对应卷登记，并在本卷 §4 表与 `02-阶段性任务/00-实施路线图` 的相应阶段打勾。
- 文档与代码互指：代码文件路径写进卷内「落地位置」，防止设计与实现脱节。
