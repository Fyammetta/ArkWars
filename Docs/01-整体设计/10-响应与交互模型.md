# 10 响应与交互模型

> 交互层：窗口开出来之后，谁先说话、能不能连环、窗何时关（统一由 UI 裁决）、玩家怎么选。`03` 定义窗口的形状，本卷定义窗口的**策略与交互**。
> 核心：一切"要不要响应、按什么顺序响应、可不可再响应"都是可配策略；响应链（抵消链）是策略的嵌套实例，不是特殊系统。

## 1. 职责边界

| 管 | 不管 |
|---|---|
| 窗口策略：全体/按序/首个；响应次序（`Priority` 降序 × 座次序；同时类策略无序） | 交易/时机/技能的本体逻辑（`03`/`04`/`09`） |
| 响应链的嵌套与终止、失效传播 | 目标与距离裁决（`05`） |
| 询问状态、关闭请求入口（关闭时机由 UI 裁决）、响应期上锁 | 客户端的选牌/表现（`11` 输入与演出侧） |
| 选择输入协议（候选 → 提交 → 校验） | 数据与账本（`07`） |

## 2. 窗口策略（`EWindowPolicy`）

| 策略 | 语义 | 典型场景（示例） |
|---|---|---|
| `All` | 名单上所有合法技能同开，各自独立决定 | 多伤害减免可同时响应 |
| `InOrder` | 按次序逐个询问，前一个不响/响完再到下一个 | "逐人询问是否出回应牌" |
| `FirstOnly` | 谁先响应生效，其余作废 | 首响抢占类 |

```cpp
// 窗口策略（`EventTypes.h` 权威，逐字——含三行语义与"粒度是技能而非玩家"的声明）：引擎实现三策略 + 层表（§2），
// 不实现任何具体问答；P3 已落三策略【骨架】（发问侧形态 + 收敛条件，见 §2 与 `13` §4.1），InOrder 有真实推演，All/FirstOnly 待 P7 接线
enum class EWindowPolicy
{
	All,          // 名单上所有合法技能同开，各自独立决定（多伤害减免可同时响应）
	InOrder,      // 按次序逐个询问，前一个不响/响完再到下一个（"逐人询问是否出回应牌"）
	FirstOnly     // 谁先响应生效，其余作废（首响抢占类）
};
```

- 策略随窗口开窗参数传入（`OpenTimingWindow`，见 `03` §4/P3 §3.2），**不进入 `FResponseWindow` 数据形状**（`03` 附录：策略不是窗口数据形状）；多轮层序另由层表配置。
- **名单序 = 技能级优先级（降序主键）× 座次（次序）**（现码实现，`P3` §3.3.2）：`Priority` 是**技能属性**——技能登记时机索引时带入（`FSkillListenerEntry::Priority`，条目落 `ArkWarSkillTypes.h`），高的先被问，只有 `Priority` 相同才比座次；座次是**局面的属性**（`05` 的 `ISeatLayout` 概念，从当前回合玩家起轮转；现码方向规则未落，只做升序）。`All`/`FirstOnly` **无序**——现实层面同时发生，各自独立决定/首响生效（排序照跑，只是策略不消费次序）。两键皆平（同优先级同座）取注册稳定序兜底——注册序只为确定性/可回放，不承载玩法语义。`FResponseEntry.Priority` = 登记优先级快照（供 UI/日志）。
- **座次于开窗时实时读取**：权威 = `UGamePhaseManagerComponent::PlayersInOrder` + `ActivePlayerIndex`（旋转起点），`CollectResponders` 每次开窗现读现算——**索引不持有座次快照**。理由：存在调换座次类效果，座次是局内活状态；若登记快照，换座技能就得对账 N 份副本，漏一处即静默错序。实时读取让换座效果的实现成本归零：只改 `PhaseComponent` 那一份权威，下一扇窗自动用新座次。
- **快照时刻 = 开窗填出 `Responders` 之时**：名单与次序自此冻结，本窗按它问到底（窗内冻结、窗外实时）；悬停期发生换座不影响进行中的窗，新座次自下一窗生效。悬停期玩家**离场**不适用本条——那是失效传播（§3，P7）的地界。
- 一个"询问事件"可拆多轮（如先逐人问 A 层、再 B 层），层序也属于策略配置，不进引擎分支。
- **引擎实现三策略 + 层表**，不实现任何具体问答。
- **三策略的差别全在【问几个人】与【何时收敛】**（发问侧只有两种形态）：`InOrder` 问一个就停、等回传推游标；`All` / `FirstOnly` 一次问全（文档：两者无序——现实层面同时发生，排序照跑、只是策略不消费次序）。收敛条件的实现 = **条目级待回账本**（`UBattleGameFlowSubsystem::ResponsePending`，与 `Responders` 等长、**技能粒度**）：关窗判据由"**发完了**"改为"**账平了**"——
  · `InOrder`：名单走完且账空即关（该策略下账本恒空，零行为变化）；
  · `All`：**发出几份 ↔ 收回几份对上才关**——按"发完即关"会把响应窗口期压成零，玩家的提交永远撞"没有活动窗口"；
  · `FirstOnly`：**响应侧首响即关**（抢占类，其余在途者的修改本就不该再生效）；**放弃侧仍等账平**——放弃不是"响应"、不构成抢占（本表第 3 行抢的是"响应"，不是"表态"），若按"有人放弃即关"，第一个人弃权即剥夺其余人的响应权。
  · **"有结局就销账"**：响应 / 放弃 / 失联 / 被拒都算结局——只记"成功响应"会让 `All` 永远收不齐（比"发完即关"更糟：**永不关窗**）。
- **授权判据随策略分派**（`ResolvePendingIndex`），**两族判据同构、只是来源不同**：`InOrder` 认游标处那一条**且 Key 须与之相符**（同一人可连占多条，只认人会让一次陈旧重放顶替另一条的响应权）；`All` / `FirstOnly` 认"提交者与所选技能**双落在待回位**"——一次问多人时服务端无从由身份推出是哪一条，须"按 Key 找"。两族共同须命中"该 `Owner` 名下"与"尚无结局"，否则拿别人的 Key 或重复提交都能销账；空 Tag（放弃入口）两族皆跳过 Key 判。**自报的 Key 始终只是"定位线索"而非"授权"**：它只能在本人名下的待回条目里挑一条，挑不出即拒。
- **同窗口对同一交易负载的修改不是并发写**：`All` 只表示"同开、各自独立决定"；各响应者对共享数值/结果位的修改是**追加请求、不覆盖共享值**（`UBattleTransaction::ModeRequests` + 唯一追加口 `AppendModification()`，见 `04` §4.1），`Execute` 前由族折叠器（`FoldMods()`）按固定序一次性收敛回填——**不按 ServerRPC 到达序**；响应者先后（窗口名单序 = `Priority` 降序 × 座次，平手取注册稳定序）只决定"谁被问"，不参与折叠计算（同 Op 数学可交换、跨 Op 族序内嵌）——保证任何局面的收敛可复现（回放见 `11` §7）。

## 3. 响应链（嵌套响应的统一形状）

响应链 = 一个"响应本身也可以被响应"的递归窗口栈：

```
链例（样本，非框架）："回应牌链"
  Use(牌X) → 目标响应窗口(可否回应)
      → 若响应，响应本身再次进入同策略窗口（他人可再回应/抵消）
      → 直到无人再响应 / 达到链深上限 → 自顶向下结算结果
```

规则由数据与策略配置表达，引擎只提供：
- 链的**栈帧**（每帧 = 一个窗口，记录响应者/响应内容/是"抵消"还是"追加"）；
- **终止条件**（无人响应 / 链深上限 / 首个抵消成功）；
- **失效传播**：链下层目标中途失效（死亡/离场）时，`05` 目标失效规则接管，往上逐帧作废。
- 结算次序：**自底向上**（最后响应的先生效），由交易/效果按帧回放。

> 无懈类、出闪类、抢出类全是同一条链的不同数据配置（谁是合法响应者、响应什么、响应内容能否再被响应）。

> **响应链 ≠ 交易嵌套（勿混）**：响应链是**同一个窗口内部的递归栈**（同窗可再被响应，自底向上结算，
> 见 §3）；交易嵌套是**交易队列的插队栈**（挂起当前交易、先完整结算另一笔再恢复，`04` §3.2）。
> 前者发生在"一个窗口内部"，后者发生在"交易之间"；两者可叠加——响应里发起新交易走排队/插队，
> 对外事件序见 `12` §6。

> **实现形态对账（P5/P7 施工依据）**：递归窗栈**不是**在窗口里开嵌套窗（`03` §7："在窗口里等待窗口"是错的），
> 落地形状 = **递归交易嵌套栈 + 每层子交易自己的查询窗**：每层响应（如打出一张无懈）= 一笔嵌套子交易
> （`04` §3.2 Push/Pop），子交易 `QueryTimings` 开的窗即"对响应的再响应"下一帧；链终止 = 某层窗口空关，
> **自底向上结算 = 嵌套栈退栈序**，天然成立、无需附加机制。链深**不由引擎侧设限**（2026-09-16 定：
> `MaxNestedDepth` 成员与超深校验已从施工面删除，`04` §3.2 不变量 2 降为设计约定）——链深交由规则表
> 与调用方账目约束：单轮打断（濒死）与循环型的迭代嵌套（决斗类深度恒 1，`04` §2 族分两型）皆恒 1，
> 无懈类递归链的叠深随 P7 规则表落地；
> 样板走查（无懈链事件序 / 决斗链轮次循环）见 `04` §2。

## 4. 询问与上锁

- 开问 = 相关玩家进入 `State.Responding`：P3 框架期以**子系统布尔闸门 + 单一收口三 API**（`IsResponding()` 查询 / `TryEnterResponseLock()` 进入 / `ExitResponseLock()` 退出）落实"窗口期无关输入被拒、关窗后恢复"——`OpenTimingWindow` 入口前置 `IsResponding()` 检查（已在响应中 → 拒绝 + 日志，锁状态不动），正式入锁 `TryEnterResponseLock()`、`CloseTimingWindow` 撤锁 `ExitResponseLock()`（锁切换瞬间各广播一次 `FResponseLockChanged`，bool = 新值；空名单直通窗不上锁）；调用方一律按 `IsResponding()` 查，将来升级 GE 时内部实现改为挂带 `State.Responding` GameplayTag 的 GE（`AbilitySystemComponent` 在 Capability Query 时按 tag 拒绝能力激活），调用方零修改。关窗即撤锁。
- **关闭时机统一只通过 UI 决定**：引擎侧不持有任何定时器（不用 Timer/`WaitDelay`）。窗口 `Timeout` 只是随候选下发给 UI 的**时间预算**；UI 倒计时结束 → 客户端**直接请求关闭**（与"放弃"同一 ServerRPC 入口，服务端按当前响应者放弃收敛），绝不悬挂——与 `02` "停在查询点等回调"契约配套。
- 自动方（锁定/全自动被动）不走询问，但依然过一遍"合法"校验，失败则跳过（有日志）。

## 5. 玩家选择输入（交互协议）

```
服务器开窗 → 下发候选（可选：目标候选 / 牌候选 / 响应或放弃；附 Timeout 时间预算）
玩家 → ServerRPC 提交选择（选了什么 / 放弃 / UI 倒计时到点 = 直接请求关闭，按放弃收敛）
服务器校验：
  ① 该玩家此刻有权响应（在 Responders 名单 & 处于 Responding 锁内）？
  ② 提交内容合法（在候选内 & 通过 05 裁决）？
  ③ 账本/代价可付（07 预检）？
  全部通过 → 作为窗口结果回写；否则忽略/回档重问
```

- 提交是**意图**不是行为：服务器校验后才触发（激活技能体 / 开下一窗口）。
- 客户端选牌交互（`FPlayerSelectionChangeDelegate` 等既有委托）留在表现侧做候选展示，**不上行裁决**。
- **下行通道 = ClientRPC 点对点，不走属性复制**（⑦ 口径，2026-09-16）：候选是事件语义（`InOrder` 同一时刻只问一人、丢了窗口就在原地悬挂），且窗口住在子系统 `TOptional` 里无复制载体、`FResponseWindow` 含 `TStrongObjectPtr` 不可序列化——形状（DTO + 两壳）与四条理由见 `11` §5.1/§5.2。
- **ModRequest 的通知链路（响应者如何把修改交进来）**：窗口开启 → 广播 `FWindowOpened` +
  逐个询问（§4）→ 响应者从窗口负载（= 交易引用）拿 `Tx` → `Tx->AppendModification(Req)`
  （`04` §4.1 唯一入口，`State == Querying` 才收）→ 关窗广播 `FWindowClosed` → 交易
  `OnWindowClosed` → `Execute` 里 `FoldMods` 折叠。**修改不是被推送进交易的，是响应者被通知后
  主动追加**；全链路、广播点与现状缺口见 `12` §4。

## 6. 取消 / 吞效果（牌被无效）的语义

"结算没生效"分两档，回滚语义相反（结果位见 `04` §4）：

| 档位 | 交易结果 | 动作与移动 | 账本 | 回滚 |
|---|---|---|---|---|
| 取消 / 防止 | `Finish(false)`（不落子收尾） | 不落子：牌不动、留原处 | 未发生 | 按来源链（`06`）回滚消耗（`07 Release`）、释放已悬停对象 |
| 吞效果（牌被无效） | `bNullified` | 照常发生（`Consume→Add` 两跳，守恒不变） | 照记 | **不回滚**——仅效果层为零，广播 `Notify.PlayCard.Nullified` |

- 回滚只属于取消/防止档（`Finish(false)`），不做全局撤销——避免结算回溯风暴；吞效果只在该效果数据声明本档时发生，不自动附加于任何出牌。
- 链上"抵消"类响应落哪一档由链配置/结果数据声明，引擎不预设。

## 7. 与邻卷契约

| 本卷对外 | 契约 |
|---|---|
| 对 `03`：窗口形状 | 本卷提供策略，`03` 提供生命周期接口；开窗签名唯一 |
| 对 `09`：技能被问/被自动 | bAskFirst 进询问，否则自动；次序 = 技能级 `Priority` 降序主键 × 座次次序（§2，登记时经 `FSkillListenerEntry::Priority` 带入；取值来源待 P6 §2 定形） |
| 对 `05`：候选与校验 | 提交前二次校验目标合法性 |
| 对 `07`：频率 | 询问前预检，触发时消耗；取消/防止（`Finish(false)`）退回（`Release`），吞效果（`bNullified`）照记不退 |
| 对 `04`：窗口收敛 | 任何结果最终 `Finish(bool)` 单收尾收敛（成功 `true` / 防止 `false`） |
| 对 `12`：事件登记 | 窗口开关广播（`FWindowOpened/Closed`）与修改追加广播（`FTransactionModified`）登记于 `12` §5.2；本卷只出策略，不出事件定义 |

## 8. 扩展点

- 新响应形式（如"必须响应否则代价"）→ 在链配置加一个策略/结果分支，不进引擎。
- 新轮询顺序（按座次变体）→ 换 `ISeatLayout` 或加顺序策略。
- 客户端新交互形态 → 只改候选下发与提交 RPC 的数据形状，裁决不动。

## 10. 案例（仅作样本，不进框架）

- "A 使用一张伤害牌，另一人可回应之"：`PlayCard.Use` 窗口 = InOrder 链第一层。案例用途：链配置样例；回应把该出牌吞掉的效果数据可声明为 `bNullified` 档（`04` §4）。
- 濒死求回应逐人询问：InOrder + 每问一个"救/不救"、可多层。案例用途：InOrder 多轮。
- 多免伤同时可开：`Damage.Incoming` 用 `All`。案例用途：策略差异。
