# 02 回合与阶段流程

> 同步主干：回合状态机、阶段语义、轮转与阶段修正。
> 本卷不含异步窗口的实现（见 `03`），只定义主干在哪**停下来开窗**。
> 落地：`UBattleGameFlowSubsystem`（FSM/驱动）+ `UGamePhaseManagerComponent`（复制载体，挂 GameState）。

## 1. 职责边界

| 管 | 不管 |
|---|---|
| 阶段序列的定义与推进、停留点语义 | 阶段内部规则（摸几张、弃牌上限）——它们是阶段体逻辑，挂为普通流程函数 |
| 阶段修正队列（SKIP/EXTRA/JUMP）的裁决 | 谁塞修正、技能干预——那是时机窗口与技能（`03`/`09`） |
| 回合轮转、活跃玩家与顺序 | 对局设置（分身份、初始手牌）——对局生命周期（`00-路线图` P1 启动线） |
| "此刻该停在哪个点等窗口" | 窗口本身的开启策略与策略轮询——`03`/`10` |

## 2. 阶段语义（三档后缀固定含义）

沿用 `EGamePhase`（`ArkWarFlowTypes.h`），三种后缀语义固定，全系统禁止再发明含义：

| 后缀 | 语义 | 执行方式 |
|---|---|---|
| `Xxx_Pre` | **查询时机点**："进入 X 前"，技能可干预（跳过/追加/触发效果） | 异步响应窗口（`03`） |
| `Xxx` | **阶段本体**：本阶段规则逻辑 | 同步执行（先直通、规则薄层按阶段接入） |
| `Xxx_Post` | **查询时机点**："X 结束时"，触发类技能挂载点 | 异步响应窗口（`03`） |

完整序列（固定序、可配表驱动，见 §7）：

```
GameStart → Begin → Preparation_Pre → Preparation → Preparation_Post
        → Judgment_Pre → Judgment → Judgment_Post
        → Draw_Pre → Draw → Draw_Post
        → Action_Pre → Action → Action_Post
        → Discard_Pre → Discard → Discard_Post
        → Finish →（下一位玩家的 Begin）
```

`GameStart` 只作轮转中转（Finish 后 → 换人 → Begin），不作停留点。

## 3. 推进模型（同步 FSM）

### 3.1 入口与门控

- 所有推进都在服务器：`IsRunningOnServer()` 门控；`SetPhase` 带 `HasAuthority` 守卫（现状已具备，保留）。
- `SetPhase` 是一次**事实**：同步广播阶段委托 + 复制（OnRep 到客户端）。客户端没有流程任务，只消费该事实。

### 3.2 `Advance()` 骨架（单步推进）

```
Advance()
 1. 应用修正队列 → Next = ResolveNextPhase(Current)          （含 GameStart 回绕=换人）
 2. 若 Next 是停留点（五大主阶段 / Begin / Finish）：
      SetPhase(Next)           事实同步
      ExecutePhaseBody(Next)   阶段体（同步；判定区遍历/摸牌/弃牌等薄层）
      下一跳 = Advance()（由驱动方再次调用）
 3. 若 Next 是 _Pre/_Post（查询时机点）：
      委托给 03 的开窗过程：OpenTimingWindow(Phase_Pre/Post)
      窗口关闭回调 → 继续 Advance()
```

> 该骨架把"开窗"抽成一次委托调用，阶段机本身不实现窗口，只约定两件事：
> **停在查询点 → 等窗口回调 → 继续**。P1 阶段窗口未接线时，该委托空转直通，序列行为与有窗口时一致（区别仅在是否等待）。

### 3.3 停留点清单

| 停留点 | P1（现） | 之后 |
|---|---|---|
| `Begin / Finish` | 直通（Begin 暂无阶段体；Finish 触发换人逻辑） | 阶段体按需挂薄层；Finish 后 `SetNextPlayerActive()` 换人 |
| 五大主阶段（Preparation/Judgment/Draw/Action/Discard） | 停留（什么都不做，等待外部 `Advance`） | 停留点内执行对应阶段体规则（薄层，按 P 阶段逐个接） |
| 各 `_Pre/_Post` | 直通（等价于"窗口空转"） | 开异步窗口（`03`），窗口策略可配 |

## 4. 阶段修正队列（SKIP/EXTRA/JUMP）

修正来自时机窗口（`03` 携带），队列化保证**一次窗口内多个修正叠加有序生效**：

| 操作码 | 含义 | 生效方式 |
|---|---|---|
| `Skip` | 跳过整个大阶段 | 整组吞掉所属大阶段（Pre/主/Post 一起，或独立阶段），落到下一大阶段门口 |
| `Extra` | 追加一个指定阶段 | 出队时优先返回 Target，顺序推进顺延 |
| `Jump` | 直接跳到指定阶段 | 出队时立即返回 Target |

```cpp
struct FPhaseModifier { EPhaseOpcode Op; EGamePhase Target; };   // Jump/Extra 用
TArray<FPhaseModifier> PendingModifiers;                          // FIFO
```

要点：阶段机只管"队列裁决"；**塞修正的通道**在 `03`（窗口响应结果的副作用）。`PushPhaseResolvation` 保留为调试/测试入口。

## 5. 轮转（回合边界）

- `Finish` 本体结束时 → `SetNextPlayerActive()`：按 `PlayersInOrder` 顺序 +1，末位回绕到 0（现有越界缺陷在 P0 修复，见路线图 P0 §2）。
- 顺位载体：`UGamePhaseManagerComponent` 的 `PlayersInOrder / ActivePlayerIndex`，均已复制 + OnRep，客户端可展示"当前回合玩家"。
- 活跃玩家变化也是**事实通知**（`FActivePlayerChangeDelegate` 保留），不开放干预。

## 6. 与邻卷的契约

| 本卷对外 | 谁消费 | 契约 |
|---|---|---|
| `SetPhase` / 阶段进入 | 客户端、阶段体注册表 | 只广播事实，不可被否决 |
| "停在查询点" | `03` 开窗过程 | 窗口关闭必须回调推进，不允许悬挂 |
| `ResolveNextPhase` 修正裁决 | `03` 写入的修正队列 | FIFO + 操作码优先级（JUMP 立即、EXTRA 顺延、SKIP 吞段） |
| 活跃玩家/顺位 | 目标裁决（05）、频率账本（07）、响应顺序（10） | 只读查询：`GetActivePlayer()/GetPlayerByIndex()` |

## 7. 扩展点

- **阶段表可配**：序列存数据表/数组（`PhaseOrder`），新增阶段只加枚举值 + 注册阶段体函数，流程循环不感知具体阶段。
- **大阶段扩展**：若未来需要（如摸牌拆为"摸牌→展示→收手"），用"阶段 = 主阶段 + 附属子阶段"的嵌套表，主推进循环不改。
- **阶段体薄层注册**：`PhaseBody` 函数以 `EGamePhase → 回调` 注册进表；技能机制要"在阶段中做规则替换"走 `03` 时机，不允许直接替换阶段体。

## 9. 案例（仅作样本，不进框架）

- "进入判定阶段前跳过判定"：某修正写入 `PendingModifiers`（Skip Judgment 整组）→ `Advance` 时吞段 → 序列从 Draw_Pre 继续。案例用途：验证 §4 队列 + 阶段机解耦。
- "追加一个出牌阶段"：写 `Extra Action` → 当前回合在 Action 之后再跑一次 Action_Pre/本体/Post。案例用途：验证 Extra 顺延语义。

## 附：本卷类完整定义（目标形态）

> 汇编口径：以本卷设计为准，合并本卷散落片段（§4）与现行源码相关成员，作为"完工后"参考；`EGamePhase`（18 态 + 三档后缀）与 `PhaseTags` 定义于 `ArkWarFlowTypes.h`（§2/§8），不重复展开。

### EPhaseOpcode（§4 表归纳，供 FPhaseModifier 引用）

```cpp
// 阶段修正操作码（02 §4 表）
enum class EPhaseOpcode : uint8
{
    Skip,   // 跳过整个大阶段：整组吞掉所属大阶段（Pre/主/Post 一起），或独立阶段
    Extra,  // 追加指定阶段：出队时优先返回 Target，顺序推进顺延
    Jump,   // 直接跳到指定阶段：出队时立即返回 Target
};
```

### FPhaseModifier / 修正队列（§4）

```cpp
// 单条阶段修正（Jump/Extra 用）
struct FPhaseModifier
{
    EPhaseOpcode Op;      // 操作码（Skip/Extra/Jump）
    EGamePhase Target;    // Extra/Jump 的目标阶段
};

// 修正队列（FIFO；Advance 出队裁决，见 §3.2 ResolveNextPhase）
TArray<FPhaseModifier> PendingModifiers;
```

> 说明：`PendingModifiers` 是推进机载体上的成员（阶段机只管队列裁决，塞修正的通道在 `03`，`PushPhaseResolvation` 保留为调试/测试入口）。现行实现以 `GameMessage::FPhaseMessage`（DSL 形态）承载修正队列（`§8` 落地表），本卷设计目标为上述结构化 `FPhaseModifier` 队列。
