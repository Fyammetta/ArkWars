# 08 卡牌与容器模型

> 全游戏最高频的落子对象：牌怎么存、怎么搬、怎么被结算引用。移动从第一天就交易化（`04`），容器只提供区域读写接口，不解释意图。
> 落地：`ICardContainerInterface` + 玩家侧 `UCardManagementBusComponent` + 桌面侧 `ACardTableManager` + `FMoveMessage` DSL（`GameMessage.*`）。

## 1. 职责边界

| 管 | 不管 |
|---|---|
| 区域的定义、容器持有、保序、进出 | 移动的时机干预（查询窗口在 `03`，交易在 `04`） |
| 移动意图描述（DSL）与解析 | 出牌的响应链/费用（`10`/使用交易） |
| 区域 Tag → 容器的唯一解析 | 每张牌的具体规则（数据侧标签声明） |
| 牌的标识/合成（含虚拟牌） | 客户端表现（`11`） |

## 2. 区域归属约定（谁持有哪片区域）

| 区域 Tag（原生标签） | 宿主 | 字段 | 语义 |
|---|---|---|---|
| `Card.Area.Hand` | 玩家侧组件 | `HandCards` | 手牌 |
| `Card.Area.Equipment` | 玩家侧组件 | `EquipmentArea`（槽数组） | 装备/持久区 |
| `Card.Area.Judgement` | 玩家侧组件 | `JudgementArea`（每牌一槽） | 判定区（同种唯一、保进场时序；收单/结算形状见 §8） |
| `Card.Area.Pile` | 桌面 `ACardTableManager` | `PileArea` | 牌堆 |
| `Card.Area.Discard` | 桌面 | `DiscardArea` | 弃牌堆 |
| `Card.Area.Cache` | 桌面 | `CachedArea` | 缓存/移出游戏类 |
| `Card.Area.Used` | 桌面 | `PlayedArea` | 使用/缓冲堆 |

- 区域标签为**开放可扩展集**（新增"展示区/特殊区/专属区"按 `03` §3.2 的合规出路补标签 + 容器字段）。
- 新区域的两步接入：容器加字段与复制/OnRep + 注册进 §4 解析表。**引擎移动流程零改动**。

## 3. 容器接口（载体随 §7 定稿为 `FArkCard`）

```cpp
UENUM()
enum class EAreaWriteResult : uint8
{
    Accepted,
    Rejected_OccupiedSameKind,   // 判定区：同种判定牌已存在（08 §8 同种唯一；正常路径由上游合法过滤前置拦截）
    Rejected_CategoryMismatch    // 判定牌类别无法收单（新增种类的兜底返回，正常路径见 08 §8；拒收原因供上层裁决）
};

class ICardContainerInterface
{
public:
    // —— 只读 ——
    virtual TArray<FArkCard> GetCardsByKey(const FGameplayTag& AreaKey) = 0;    // 区域格位视图
    virtual const FArkCard* GetCardById(int32 CardId) const = 0;                // 本容器内按实体 Id 反查；跨区定位见 §4
    virtual TArray<int32> Select(const FGameplayTag& AreaKey, const FString& Msg) = 0;  // 依 DSL（谓词/NUM/ORDER）选出命中牌的实体 Id；谓词只读 Tags
    virtual TArray<FGameplayTag> GetAreaKeys() const = 0;

    // —— 写：跨区移动 = 交易编排的两跳读写，各端只落自己名下的区域 ——
    UE_NODISCARD virtual TArray<FArkCard> Consume(const FGameplayTag& AreaKey,
        const TArray<int32>& CardIds) = 0;                          // 源侧：按实体 Id 整壳取出；返回值必须被使用（见下）
    virtual EAreaWriteResult Add(const FGameplayTag& AreaKey,
        TArray<FArkCard>&& Cards, const FString& Msg) = 0;          // 目标侧：按 Msg 的 _Order/_bDiscard 落位
};
```

- **`MoveIn`/`MoveOut` 已废除**（早期"跨区搬移"占位接口，历史快照见 `_archive`）：容器不再持有另一侧引用、不解释移动意图。跨区移动 = 交易/管理器在 `Execute` 编排的两跳读写（`§6`）——源容器 `Consume` 按实体 `Id` 整壳取出，目标容器 `Add` 落位；**两端各只改自己名下的区域**。
- 落子依据仍是意图原文：源侧 `Select` 依 DSL（谓词/`NUM`/`ORDER`，只读 Tags）选出命中牌的实体 Id，`Consume` 只负责按 `Id` 整壳移出；目标侧 `Add` 按 `Msg` 的 `_Order` 决定入顶/入底、`_bDiscard` 决定弃牌语义。
- 卡的存放载体 = `FArkCard`（`Tags` 语义 + `Id` 实体身份，定义见 §7.1）。**谓词吃 `Tags`、结果带 `Id`**：筛选/条件只读卡牌标签（DSL 解析零改动），但被"选中/移动/消耗"的牌必须整壳 `FArkCard` 随行，禁止剥壳裸传容器导致实体引用丢失。
- **`Consume` 的返回值必须被使用**（签名标 `UE_NODISCARD`）：`Consume` 是按 `Id` **移出**——牌一旦取出即离开源区，返回值必须被**立即接手**（原样喂给目标 `Add`、或进入消耗/结算去向，见 §7.4），禁止丢弃/只取不落——丢弃返回值 = 牌凭空消失，破坏"任意移动全局卡牌总数不变"的守恒对账（P2 验收项）。只看不拿用只读接口（`GetCardsByKey`/`Select`），`Consume` 不存在"查询"用法。
- 复制：区域采用 `FFastArraySerializer`（条目 `ItemID = Card.Id`，见 §7.1）——标记/衍生改动只同步单条，并规避"元素内嵌动态容器的 replicated 结构数组"的复制不确定性；各区域独立 OnRep（客户端可分辨哪区变了）。

## 4. 区域解析（唯一入口）

```cpp
ICardContainerInterface* UBattleFunctionLibrary::ResolveContainer(AActor* Owner, const FGameplayTag& Area)
  Owner 为空             → nullptr（无归属；调用方自行兜底 / 判失败）
  Owner 自身实现容器接口 → Owner 自身（ACardTableManager、ABattlePlayerState 均如此）
  否则                   → Owner 名下首个 ICardContainerInterface 组件（Area 有效时优先命中持有
                           该区域的组件）；都没有 → nullptr
```

- 落点 `UBattleFunctionLibrary::ResolveContainer`（`Battle/Toolkits/`），**全局只有这一处**做
  "归属 Actor → 容器"映射；交易/阶段体/技能一律经它，杜绝散落判断。
- **类型链**：入参 `AActor*`（交易经公开 `Instigator`/`Targets`（`TWeakObjectPtr<AActor>`）承载
  `AActor*`）；早期草稿的 `APlayerState*` 作废。`Area` 为区域标签：两端 Actor 各自持有其区域集合
  （`GetAreaKeys()`），解析不按区域分派，`Area` 仅用于组件兜底分支的多组件择优。
- **归属规则**：`Owner` 为空 = 无归属 → `nullptr`（当前不存在无主落子路径：桌面 Actor 由交易
  `Instigator` 承载、玩家侧由 `Targets[0]`（`ABattlePlayerState`）承载）。
- **玩家侧落点**：解析为 `ABattlePlayerState` **自身**（其自身实现接口），再由其**内部转发**至
  `UCardManagementBusComponent`（逐区域 `GetAreaKeys().Contains(Area)` 命中后转发）。
- **跨区实体反查（`FindCardById`）**：按实体 Id 遍历 §2 注册表内所有容器定位所在区，返回所在容器与槽位。素材的"在场校验 / 消耗定位"（§7.4）经此单点，不散落遍历。

## 5. 移动意图 DSL（`FMoveMessage`）

`CardMsgDef` 的 DSL 保留为**交易的输入描述**（交易的意图载体，见 `04`），解析器已随 P0 修复；完整 DSL 表在路线图 P2 §测试表：

| 片段 | 含义 |
|---|---|
| `NUM=n` | 数量（默认 1） |
| `FROM=区域码 / TO=区域码` | 源/目标区（`-AP/-AH/-AD/-AE/-AJ/-AS...`，含用户缩写映射） |
| `AREA=Skill.Foresee` | 特殊/技能专属区目标 |
| `CONDITION:SUIT=/H`、`MIN/MAX`、`PREDICATE` | 过滤条件（选中哪些牌） |
| `ORDER=Top/Random/Bottom` | 取牌顺序 |
| `DISCARD=1`、`IsDiscard` 键 | 显式弃牌标记（决定是否触发弃牌事件） |
| `_Meta` | 原文保留（容器落子/日志/回放用） |

修复纪律（P2 复核结论保留）：解析判真一律 `Find(...) != INDEX_NONE`；值解析不复用上一个键的残留 `Temp`。

## 6. 移动的查询与通知（对齐 `03`）

```
意图(FMoveMessage) → UCardMoveTransaction（04）
  → 查询时机 Card.Move（可改数量/去向/取消）         —— 通常无人响应，窗口空转成本可忽略
  → Execute：交易编排两跳读写（本卷 §3）——源容器 Select 按 DSL 选 Id → Consume 按 Id 整壳取出 → 目标容器 Add 落位
  → 通知：Notify.Card.Moved；细分 AreaEntered/AreaLeft 供"装备入场"类技能订阅
```

- **弃牌过滤**：带 `DISCARD=1`/`IsDiscard` 的 DSL 移动解析落位为 `FMoveMessage::_bDiscard`（字段在 `GameMessage::FMoveMessage` 已存在，§5 表"显式弃牌标记"），表示"这是按一次弃牌动作触发的移动"——时机层据此区分整理/摸入/弃牌，避免把一次 `NUM=N` 的整批弃牌拆成逐张触发多次弃牌事件；不另立字段。
- **同区 `_From == _To` 不再走容器改序**（09-09 决策：`SetCardOrder` 废弃）：手牌整理
  （玩家改序）是 UI 表现层行为，服务器不发起同区移动/改序交易——`UCardMoveTransaction`
  对同区短路 `Finish(false)`（P2 §2-D）；区数组顺序 = 服务器落子序（两跳 `Add`），效果
  "取区顶/底"依该序，玩家手牌呈现序由 UI 自理、不写入服务器。

## 7. 牌模型：卡牌值类型 + 出牌素材

### 7.1 卡牌值类型（存放/移动层的统一载体）

- 牌在**存放与移动层**统一为 `FArkCard`——区数组、移动/使用交易载荷、检索/选择结果一律携带它，不再裸传 `FGameplayTagContainer`；语义层（DSL 谓词/条件/事件）只读其 `Tags`，谓词签名与解析不动。静态数据（图面/语音/组件类）由数据行按 `Card.Class.*` 提供，与运行期 `Tags` 以固定键衔接。

```cpp
USTRUCT()
struct FArkCard
{
    int32 Id;                     // 实例 id：服务器分配、整局唯一、不复用；0 = 无实体
    FGameplayTagContainer Tags;   // 语义单一权威：Card.Class/Suit/Point + 衍生（Card.Mark.*）
};
```

- 运行期实例的"可见身份" = `Tags`（种类 + 花色 + 点数 + 标记）；`Id` 承担实例唯一身份——同款多张可区分、可定位、可消耗。旧 `FConvertedCard/FHandCardInfo` 指针别名方案废弃：指针/弱引用不适用 RPC，值模型以 `Id` 维持实体引用。
- **Id 权威**：一切"产生牌"的入口（发牌/洗回/虚拟牌生成）经服务器分配器（`FCardIdAllocator`）单调发号、整局不复用，客户端无写入路径；单机/编辑器模式由本地兜底分配器接管。区写入点 Debug 断言"同 Id 唯一、移前存在"。
- **判同**：显式接口 `FindCardById/ContainsById`（`SameEntity` = Id 相等）；`FArkCard` 的 `==` 不做"只比 Id"重载——"同款不同实体"的全等比较仍合法。
- **复制**：区域采用 `FFastArraySerializer`，条目 `ItemID = Card.Id`——改标记/衍生只同步单条，并规避"元素内嵌动态容器的 replicated 结构数组"的复制不确定性（§3）。

### 7.2 出牌素材（`FCardMaterial`）

- 使用/打出入口（`04` 使用类交易）统一拿到"这一张要出的牌" = 形态 + 呈现身份：

```cpp
UENUM()
enum class ECardMaterialKind : uint8 { Entity, Converted, Virtual };   // 实体 / 转化 / 视为

USTRUCT()
struct FCardMaterial
{
    ECardMaterialKind Kind;   // 素材形态
    FArkCard Presented;       // 规则看到的"这一张"（呈现身份）
};
```

- 三类形态与消耗：

| Kind | `Presented.Tags` | `Presented.Id` | 消耗 |
|---|---|---|---|
| `Entity`（实体本身） | = 区域内真实牌自身（须与区一致，可校验） | 实体 Id | 按 Id 走移动交易送结算去向 |
| `Converted`（转化） | 目标种类键 + **原牌花色点数**（"转化一张与特定牌花色点数相同的牌"即此意） | 原实体 Id | 按 Id 移动原实体（实体照常离区） |
| `Virtual`（视为） | 无花色点数的选定牌身份（虚拟对象 = 临时标签组合 + 来源链，`06`） | 0（无实体） | 不移动，素材直接走效果 |

- **转化/视为都是"使用瞬间的呈现视图"**：素材不落区、不改写存储态；转化产物的 `Presented.Id = 原实体 Id`，需要实体原样（原种类确认、结算追溯）时按 Id 回查区即得（本容器 `GetCardById`，跨区经 §4 便捷入口）——一次使用里"呈现身份"与"实体身份"两层并存且不冲突，无需同时传两份牌。
- 允许"转化为哪张特定牌、转化门槛（如须同花色同点数、或须带某标记）"一律由数据/技能声明给出；引擎只认"素材 = 形态 + `Presented`"，零具体牌/技名。
- **候选集合由授权层产出**：某牌此刻可当作什么身份使用，由使用入口按技能授权上下文枚举（§7.4 合法化），不从区里按目标 `Class` 扫 `Tags`——呈现身份是上下文授权，不是牌自身属性。

### 7.3 标记 / 稳定分组

- **标记 = 挂在牌实例上的效果来源**：干员技能/效果可给特定牌实例加标记（带来源，清除规则由数据声明，统一模型见 §7.6）；引擎不特判任何标记名，查询走实例数据接口（命名空间 `Card.Mark.*`），**标记不进身份标签、不参与分组推导**（分组仍只走注册表，见下）。标记最常见的用途之一是**授权该牌的"替代身份"**：带某标记的牌可依 §7.2 的转化/视为形态当作指定特定牌使用/打出（样本见 §11，如"共振"标记 → "共振装置"）。
- 需要"角色牌/限定牌进手"等概念时走相同模型：区域任意 + 数据行类型化，**不进引擎特判**。
- **稳定分组身份 = 分类注册表声明**：牌需归属稳定分组（如"伤害类"，供状态做"禁止使用/打出某组牌"类封锁，`06` §2.3）时，以**分组注册表**登记，查询统一 `表.Contain(种类)`；分组不靠标签推导——开放标签只表达特征，分组表达归属，引擎判断一律查表。

### 7.4 落地分工备忘（实施时对照）

- **素材载荷**：使用/打出入口统一携带 `FCardMaterial`（`Kind` + `Presented`）；`Presented.Id` = 实体引用（视为 = 0），`Presented.Tags` = 呈现身份/目标种类键；来源链（授权效果追溯）随交易承载，不裸透传容器。
- **合法化先于执行**：实体/转化校验实体在场（按 `Presented.Id` 经 §4 定位查区域）；转化/视为查**授权声明**（`GrantedUse`：目标种类 + 门槛，如须同花色点数 / 带某标记）+ 频率账本（`07`）+ 使用门槛（`05` §3.2）。授权与门槛只读数据，裁决函数零具体牌/技名。
- **执行**：实体/转化按 `Presented.Id` 走移动交易送 `Used`；效果侧按 `Presented.Tags` 的目标种类键取组件/数据——`CardComponentBase::Get` 的键 = 素材 `Presented.Tags` 的 `Card.Class.*`（组件键"解码"待办随此定稿）；视为不移动，虚拟素材直接走效果。
- **效果段读结果位**：移动段落定后、触发效果前读交易 `bNullified`（`04` §4）——置位则跳过效果段（实体仍已落结算去向；虚拟素材本就无移动，直接零结算）；拦截改写发生在族窗内的窗口/技能体（样板 `09` §11），本卷不特判。
- **标记 v1**：作为实例标签容器上的扩展标签（命名空间 `Card.Mark.*`），身份/分组解析只用固定键故不受影响；任何标记名只在内容侧声明。标记与"卡牌标签 vs 玩家标签"的统一模型待专门评审后定稿。

### 7.5 迁移面与实施时序

- **迁移面（机械替换，谓词/DSL 不动）**：`ICardContainerInterface` 与区字段、`FMoveMessage`/`UCardMoveTransaction` 载荷、筛选/选择/展示结果、`Try*` 入口与 RPC → 一律 `FArkCard`；使用类交易载荷 → `FCardMaterial`。铁律：**谓词吃 `Tags`、结果带 `Id`**——任何"选中一张牌"的 API 只传 `FArkCard`，禁止剥壳裸传导致实体引用丢失。
- **实施时序**（与路线图 P 阶段对齐，施工以路线图为准）：
  1. 结构定稿：`FArkCard`/`FCardMaterial` + `FCardIdAllocator`，区复制切 `FFastArraySerializer`；
  2. 全签名迁移 + `GetCardById`/§4 跨区便捷定位；
  3. 移动/消耗按 Id + 槽字段（`ORDER` 表达插入策略）+ 区唯一断言；
  4. 使用类交易接 `FCardMaterial`，`CardComponentBase::Get` 按 `Presented` 取键；
  5. 合法化层（授权/频率/门槛）产出候选素材，收口"转化/视为"入口。

### 7.6 Tag 生命周期（终结条件声明）

- **问题**：牌实例身上的衍生标签（`Card.Mark.*` 及未来区上下文类标签）何时"终结/失效"，不能靠散落的"离区布尔"或区域特判——区域特判必然按区域枚举，新增区域/新增标签都要改分支。
- **终结原因收口为三类**（标签声明自己属哪类，`任一条满足即终结`，默认永久 = 随卡实体生命周期）：

| 终结类别 | 触发 | 说明 |
|---|---|---|
| `主动移除` | 显式解除动作（效果/规则要求去掉该 Tag） | 不依赖移动；任何显式 Remove/清除操作即终结 |
| `离开附加者（任意区域）` | 卡脱离它的"附加者"（宿主对象）——**不论随后进哪个区域** | 依附对象被移除/宿主解体时终结，与去向无关；由移动事件（宿主/附加者离场）驱动 |
| `进入弃牌堆` | 卡落入 `Discard`（真弃置，`Used→Discard` 段） | 弃牌堆 = 重置位，入弃即终；`Used` 缓冲堆不算，见 `04` 弃牌语义 |

- **落地分工**：
  - 终结类别是**引擎实现**（哪类标签在哪个生命周期点被剥离），不再按标签名特判。
  - 每个 Tag 属哪几类终结 = **数据/标签注册声明**（如"随牌走 / 随附加者走 / 入弃即清"三选或组合）；查询侧只读 Tags，不感知终结。
  - 移动类终结的执行位 = **交易移动编排的两跳之间**（§6：源 `Consume` 后、目标 `Add` 前，或在进入 `Discard` 目标侧判定），不在阶段体/技能体散落清理。
- 示例（仅形状）：某技能给角色装备区的牌挂的"装备技"类标签声明 `离开附加者`（随装备离场即失效，见 `09` §6）；使用痕迹类标签声明 `进入弃牌堆`（入弃清，防误复生/复活带痕）。

## 8. 判定区：收单约束与结算形状（抽象）

判定牌是"先放置、后延结算"的牌类通用形状：经使用裁决后进入某角色的判定区，到该角色判定阶段统一结算。区域层不解释判定意图（§1 边界不变），但判定区携带两类**结构性不变量**，收单方、结算体、转移路径据此编程，互不重复判断：

### 8.1 区域不变量

- **同种唯一**：判定区对每种判定牌至多容纳一张。这是区域级数据约束，不是某张判定牌的个性规则；任何新判定种类自动继承。
- **保进场时序**：每次收单记录进场序号；结算顺序由此导出（见 §8.3）。

### 8.2 收单（进入判定区）

- **正常使用路径**：目标合法性裁决（`05` §3.2）已把"目标判定区已含同种"者过滤掉，落位即视为合法。区域/收单侧只执行落子与不变量维护，不做"拒收"语义。
- **转移路径**（判定结果驱动的牌位交接，如移交相邻座次）：若落点已含同种，一律顺延下一座次，直至空位；由同种唯一保证顺延必然收敛。不存在"放置失败"终局——转移要么落位，要么整条因无空位而由发起方裁决取消。
- 复制/表现：判定区内容与进场序号随区域属性复制（§3、`11`），客户端无写入路径。

### 8.3 结算（判定阶段）

- 判定区所有判定牌统一在持有者判定阶段结算（`02`）；顺序 = **后入先判（LIFO，按进场序号倒序）**。
- 判定阶段体只按 LIFO 逐张驱动"亮出判定牌（取牌堆顶）+ 读结果 + 离区"三步（施工见 P5）；每张的**离区方向与结果效果**（伤害/状态/转移）由判定结果的效果描述符决定（`06`），阶段体与容器不做判定牌特判。
- 转移只可能由判定结果驱动；不存在"收单失败即转移"规则（§8.2 已保证正常路径与转移路径都无放置失败）。
- **离区默认去向 = 弃牌堆**：结算后未走转移的判定牌由判定区移入弃牌堆（移动交易），并以**判定者（该判定区持有者，即本张判定的执行玩家）**为弃置来源广播通用弃牌事件（`03`/`04` 弃牌语义，视为判定者弃置一张牌）；转移类结果则改为移动交易接力到目标判定区，不广播弃牌事件。
- 亮出与结果对全桌公开，属事实通知通道（`03` 的 `Revealed` 族），不开"防"的查询窗口。

## 10. 扩展点

- 新区域 → 加容器字段 + 解析表行 + 复制注册（三处，均在数据/注册面）。
- 新移动语义（如"置于牌堆顶/底、插入指定位置"）→ 容器接口加定位参数，交易复用。
- 新牌类型 → 数据行 + 标签，引擎无改动。

## 11. 案例（仅作样本，不进框架）

- 摸牌阶段摸 N：阶段体薄层 → `FMoveMessage("NUM=n FROM=-AP TO=-AH")` 交易。
- 判定：判定阶段按判定区进场时序 LIFO 逐张结算（§8）：每张先亮出牌堆顶（落入判定区临时位）→ 读花色/点数结果 → 判定牌按结果离区（无转移 → 进弃牌堆，以判定者为来源广播弃牌事件；转移 → 落到下一座次判定区）——所有移动全走同一交易。
- "视作使用了一张牌"：虚拟牌标签组合 + 使用交易，不消耗实体牌。
- "共振"标记 → "共振装置"（样本）：带标记的牌可当作指定卡使用/打出——标记授权"替代身份"的形状演示；具体素材与门槛（走转化或视为、花色点数要求）由数据声明给，引擎无"共振"概念。
