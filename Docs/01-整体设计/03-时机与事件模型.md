# 03 时机与事件模型

> 贯穿全体系的连接件：把"会发生的事"与"已发生的事"分两条通道，让技能在任何结算点获得介入权而不侵入流程。
> 落地：时机总线（流程宿主）+ 标签体系 + 窗口基座（与 `10` 配合成完整响应交互）。

## 1. 职责边界

| 管 | 不管 |
|---|---|
| 时机/事实标签的分类、命名、注册 | 标签被谁监听、唤醒次序以外的内容 |
| 窗口的开启/关闭、负载构造 | 窗口内逐人询问策略、超时后行为（`10`） |
| 交易在哪些时机被查询/通知（与 `04` 对齐） | 交易的执行细节（`04`） |
| 事实通知的广播形态 | 客户端的表现（`11`） |

## 2. 两条通道（本模型的第一原则）

```
事实通知通道（同步多播委托 / RepNotify；保留现有形态）
    FGamePhaseChangeDelegate / FActivePlayerChangeDelegate / ...
    含义：事情已发生。订阅者只读、只反应，不可否决。

查询时机通道（新增：异步响应窗口；标签 Event.Timing.* + 负载）
    含义：事情将发生。响应者可修改、阻止、替代、追加。
```

> 事实通道的**完整委托清单**（谁广播、何时广播、谁订阅、怎么登记）集中登记于 `12` §3；
> 查询通道的**通知链路**（开窗 → 通知 → `AppendModification` → 关窗）见 `12` §4。

**绝不混用**：把可干预的查询放到通知通道 = 反应者失去介入权；把已发生的事实开成窗口 = 全局卡死。评审守则：新增事件时先回答"它已被事实化了吗"。

## 3. 标签体系

### 3.1 命名空间

```
Event.Timing.*     查询时机（将发生，开窗口）
  Event.Timing.Phase.{PhaseName}.Pre / Post    进/出阶段前与阶段结束时（03）
  Event.Timing.Phase.{PhaseName}.Start         阶段本体开始（可选，供"阶段内全自动被动"）
  Event.Timing.Card.Move                       牌移动前（可干预）
  Event.Timing.Card.AreaEnter / AreaLeave      牌进/出区域时（对技能的查询面）
  Event.Timing.Damage.Incoming                 将受到伤害
  Event.Timing.Damage.Dealt                    造成伤害时（来源侧查询）
  Event.Timing.Dying                           濒死求回应
  Event.Timing.PlayCard.Use                    牌将使用（主动出牌：效果结算起点，响应链起点）
  Event.Timing.PlayCard.Respond                牌将打出（应答付出：作为对某窗口的响应付出牌，如出杀/出闪，见 `10`）
  （出牌动作分两族、各开各窗：Use 主动使用并产生牌效果；Respond 是"应答付出"——如响应杀/闪而打出，通常无自有效果，其价值即响应成立本身）

Event.Notify.*     事实通知（已发生，同步）
  Event.Notify.Phase.Entered                   阶段已进入
  Event.Notify.Phase.Exited                    阶段已离开
  Event.Notify.Card.Moved                      牌已移动（汇总）
  Event.Notify.Card.AreaEntered / AreaLeft     牌已入/已离区
  Event.Notify.Damage.Applied / Prevented      伤害已结算 / 被防止
  Event.Notify.PlayCard.Played                 出牌已发生（使用/打出皆计）
  Event.Notify.PlayCard.Nullified              出牌被吞效果（`bNullified`：移动与账本照常，见 `04`）
  Event.Notify.Dying.Resolved / Saved          濒死结束 / 被救回
```

### 3.2 存在性与注册（引擎结论存档）

- **原生标签声明即存在**：`UE_DEFINE_GAMEPLAY_TAG` 在 `.cpp` 定义；本仓库全部静态标签（阶段/区域/花色/点数/身份/语音/时机）都走这一形态，不依赖 ini 与模块初始化顺序。
- **`RequestGameplayTag` 只查不造**：查无即无效标签并 ensure。标签是封闭集合，运行期没有合法造标签手段。
- **匹配不依赖注册**：`HasTag` 是纯名字比较；注册只影响构造与编辑器选择器。
- 数据驱动标签只有两条合规出路：① 有限常量集 → 原生标签；② 策划维护的开放集 → 单个 GameplayTags 数据资产挂到 `DefaultGameplayTags.ini`。
- 新增时机/通知标签 → 一律在新标签 `.cpp` 中 `UE_DEFINE_GAMEPLAY_TAG` 定义。

## 4. 窗口基座（与 `10` 的分工）

本卷定义**窗口的形状与生命周期接口**；`10` 定义**询问与交互策略**。窗口描述：

```cpp
struct FResponseWindow
{
    FGameplayTag TimingTag;              // 本次窗口对应的查询时机
    TObjectPtr<UBattleTransaction> Tx;   // 关联交易（可空：纯阶段时机，如 Phase.*.Pre）
    TArray<FResponderEntry> Responders;  // 合法响应者名单（技能实例 + 所属玩家）
    float Timeout;                       // 下发给 UI 的时间预算（秒）：关闭时机统一只通过 UI 决定，倒计时到点 UI 直接请求关闭（引擎侧不挂定时器）
};
```

窗口生命周期（服务器）：

```
Open（构造响应者名单 → 通知可响应） → 按策略收响应 → 汇总结果 → Close
                                           （UI 请求关闭（含倒计时到点）/全员放弃 = 空结果关闭）
```

- **负载携带**：查询时机经 `FGameplayEventData::OptionalObject`（或等价字段）携带交易引用；响应者据此读取，修改一律经交易收口 `AppendModification`（`04` §4.1），不得直写负载字段。
- **开窗者**：阶段机停在查询点（`02` §3.2）与交易 `QueryTimings`（`04`）共同调用同一开窗入口，杜绝两套窗口实现。
- **关闭 = 回调**：窗口关闭只做两件事——把结果回写（交易字段/修正队列），回调持有者继续推进（阶段机 `Advance` 或交易 `OnWindowClosed`）。
- **通知链路（响应者如何被通知、修改如何进来）**：`Open` 时按 `TimingTag` 查索引填 `Responders`
  → 广播 `FWindowOpened`（`12` §5.2）→ 按策略逐个询问（`10` §4/§5）→ 响应者从负载（= 交易引用）
  拿 `Tx` 并调 `Tx->AppendModification(Req)`（唯一收口，`04` §4.1）→ `Close` 广播 `FWindowClosed`
  → 回调持有者。**ModRequest 不是被推送进交易的，而是响应者被通知后主动追加**；端到端链路与
  现状缺口（`QueryTimings` 现只置 `Querying`、无开窗无通知）见 `12` §4。

## 5. 响应的发现（时机索引）

- 技能注册时（`09`）由 `USkillManagerSubsystem` 建 **时机 → 技能监听列表** 索引：开窗时直接查表拿候选，不做全量遍历。
- 候选只表示"这个时机有技能在听"；是否真唤醒由 `10` 的策略（优先级排序 + 逐人询问/自动激活）决定。
- 事实通知侧不需要索引：它走既有委托/GameplayEvent 的广播订阅。

## 6. 与交易的对齐（`04` 的挂机点）

交易在 `Start()` 后、`Execute()` 前调用 `QueryTimings()` 逐个开查询窗口；窗口结果（修改/防止/替代）收敛到交易的 `OnWindowClosed()`，最终统一走 `Finish(bool)`：有可落子结果 → `Execute()` → `Finish(true)`；被防止/无效 → `Finish(false)`（不 Execute，`04` §2 单收尾）。**交易不自己发窗口事件**，只声明自己在哪些时机被查询/通知——对齐表：

| 交易 | 查询时机 | 事实通知 |
|---|---|---|
| 移动 | `Timing.Card.Move` | `Notify.Card.Moved`（内再细分 `AreaEntered`/`AreaLeft`） |
| 伤害 | `Timing.Damage.Incoming / Dealt` | `Notify.Damage.Applied / Prevented` |
| 濒死 | `Timing.Dying` | `Notify.Dying.Resolved / Saved` |
| 出牌·使用（主动） | `Timing.PlayCard.Use`（响应链起点） | `Notify.PlayCard.Played / Nullified`（内再含 `Card.Moved` 细分） |
| 出牌·打出（响应） | `Timing.PlayCard.Respond` | `Notify.PlayCard.Played / Nullified`（同上） |

**交易中插入交易**：交易在窗口悬停期或落子前需要"先结算另一笔交易"时，有两条路——**排队**
（`EnqueueTransaction`，不打断，等当前收尾后自然轮到）与**嵌套插队**（`PushNestedTransaction`，
挂起当前、先完整结算子交易再恢复）；**只能在交易边界发起**（窗口回调 `OnWindowClosed` 内或
`Execute` 入口），`Execute` 中途不可挂起。机制、不变量与骨架见 `04` §3.2；对外事件序
（`FTransactionNested` → 子 `Finished` → 父 `Finished`）见 `12` §6。本卷 §7 的"多事件聚合"
扩展点即指此路——**在窗口里等待窗口**是错的，插队应交给交易队列。

## 7. 扩展点

- **新时机族**：新增一类"事件"（如"失去体力"）时：命名空间补族 + 交易对齐表补行 + 在相关卷登记。三处动作，不碰引擎主干。
- **窗口负载多样性**：负载 = 交易引用或结构化 payload（`FGameplayEventData` 已能携带 Tag/Instigator/Target/OptionalObject），必要时自定义负载类型，但**开窗/关窗签名不变**。
- **多事件聚合**：若出现"连击结算到一半出第二段"，应建模为**新交易入队/嵌套**（`04` §3.2：排队 vs 嵌套插队），而不是在窗口里等待窗口——避免窗口变解释器。

## 9. 案例（仅作样本，不进框架）

- "伤害进来前，目标宣一个防御技挡 1 点"：`UDamageTransaction.QueryTimings` 开 `Damage.Incoming` → 目标侧技能（监听该时机 + 处于可发动态）被询问 → 响应追加 `Add(-1)` 修改请求（减 1 = 负值 `Add`；多修改折叠见 `04` §4）→ 窗口关 → `Execute` 按修正值落。案例用途：验证查询通道可**改交易字段**。
- "进入判定阶段前跳过判定"：`Phase.Judgement_Pre` 窗口响应把 `Skip` 写入修正队列。案例用途：验证阶段机（`02`）与时机（本卷）的接线。
- "装备入场时发动"：`Notify.Card.AreaEntered`（`Equipment`）作为**事实**订阅挂点——不是查询，不许否决，只许追加效果。案例用途：验证两通道边界。

## 附：本卷类完整定义（目标形态）

> 汇编口径：以本卷设计为准，把 §4 窗口基座与窗口负载依赖的类型合并为"完工后"完整定义（响应者条目 `FResponderEntry` 的完整定义即下方小节，与 `10` 询问策略/`P3` §3.2 的实现对齐）；`EWindowPolicy`（`10` §2）及逐人询问/超时策略属 `10` §2/§4，不是窗口数据形状，不在此定义。

### FResponderEntry（§4 `Responders` 条目类型）

```cpp
// 窗口内一条可响应项：开窗时由时机索引（§5）+ 合法预检产出
struct FResponderEntry
{
    UBattleTransaction* Tx;            // 关联交易（窗口负载；纯阶段时机可空）
    int32 Priority;                    // 本窗内响应次序（`09` ResponsePriority；同值按座次稳定序，`10` §2）
    TObjectPtr<APlayerState> Owner;    // 响应者所属玩家
    FGameplayTag SkillTag;             // 响应者技能标识（时机索引的键值来源）
};
```

### FResponseWindow（§4 窗口基座）

```cpp
struct FResponseWindow
{
    FGameplayTag TimingTag;              // 本次窗口对应的查询时机（Event.Timing.*，见 §3.1）
    TObjectPtr<UBattleTransaction> Tx;   // 关联交易（可空：纯阶段时机，如 Phase.*.Pre）
    TArray<FResponderEntry> Responders;  // 合法响应者名单（开窗时由时机索引 + 合法预检填出）
    float Timeout;                       // 下发给 UI 的时间预算（秒）：关闭时机统一只通过 UI 决定，倒计时到点 UI 直接请求关闭（引擎侧不挂定时器）
};
```

生命周期（服务器，§4）：
- `Open`：按 `TimingTag` 查时机索引构造 `Responders` → 通知可响应；`Tx` 作为负载携带（经 `FGameplayEventData::OptionalObject` 或等价字段）。
- 收响应：按策略（`10`）逐个询问/自动激活；响应者对交易字段的修改一律经 `Tx->AppendModification`（`04` §4.1）收口，不直写结果位。
- `Close`：只做两件事——结果回写（交易字段/修正队列）+ 回调持有者推进（`02` `Advance` 或 `04` `OnWindowClosed`）；UI 请求关闭（倒计时到点直接请求关闭）/全员放弃 = 空结果关闭，任何路径不悬挂。**关闭时机统一只通过 UI 决定，引擎侧不持有定时器**（`10` §4）。
