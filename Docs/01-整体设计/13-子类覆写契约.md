# 13 子类覆写契约

> **本文档是写子类时的第一入口。** 引擎侧只提供抽象形状，具体机制一律由子类填充（`01` §6 扩展模型：
> "新增机制 = 数据组合 + 接口实现"）；本文把"现有每个基类要你覆写什么、每个钩子承担什么职责、
> 哪些默认体已经够用、哪些纪律是硬性的"一次讲清。
>
> **代码为准，本文为账**：钩子签名与调用点以源码为权威（行号随源码走），本文只登记"职责与义务"。
> 改钩子时两侧同改。

---

## 1. 职责边界

**本文管**：引擎侧**已存在**的基类与其钩子——覆写义务的档位、每钩子的职责与禁止事项、
调用点清单（硬性钩子的"崩在哪"）、以及"新建一个子类"的施工核对表。

**本文不管**：具体技能/卡牌/玩法模式**长什么样**。那是内容侧设计（`09` §11 案例、`08` §7、各卷「案例」）。
本文只说"引擎何时以什么参数来调你、你必须做什么、你不得做什么、你不做什么会怎样"。

| 你想知道 | 去哪 |
|---|---|
| 钩子**何时**被调、调用链什么样 | `03`（时机索引）、`04`（交易生命周期）、`09` §6（技能宿主）、`10`（窗口与询问） |
| 钩子**该做什么**、**不得做什么** | **本文** |
| 具体机制怎么拼装成一件技能/一张牌 | 各卷「案例」小节（`09` §11、`08` §7） |
| 某个委托/事件谁广播谁订阅 | `12` 事件与委托总表 |

## 2. 义务三档

| 档 | 形态 | 不覆写的后果 | 在册数 |
|---|---|---|---|
| **硬性（宏）** | `PURE_VIRTUAL(...)` | **调用点 `LowLevelFatalError` 崩溃**——不是"什么都不做" | 14 处，§2.1 |
| **硬性（接口）** | `= 0` | **编不过**（抽象类不可实例化） | 12 处，§2.2 |
| **软性** | 虚函数带默认体，但**默认体无实际语义** | 能编能跑，**行为缺失且静默**（最难查的一类） | §4 各基类"软性"栏 |
| **可选** | 虚函数带默认体，**默认体即合法终态** | 无需覆写 | §4 各基类"可选"栏 |

### 2.1 `PURE_VIRTUAL` 全表（14 处）

**这一档必须理解到位**：`PURE_VIRTUAL` **不是空实现**，它展开为 `LowLevelFatalError`——**调用即致命**。
换来的是类可以 `NewObject`（UObject 不允许 C++ 纯虚函数），代价是漏覆写的报应落在**调用点**而非编译期。
**故调用点清单一律列出**，供症状回查："某处莫名 `LowLevelFatalError`" → 查本表对应行的调用点。

|---|---|---|---|---|

| 2 | `USkillComponentBase` | `RegisterActivateTiming` | **零调用点**（子类自选挂载点，见 §7） | **业务本体** |
| 3 | `USkillComponentBase` | `UnRegisterActivateTiming` | `SkillComponentBase.cpp:19`（基类 `EndPlay` 兜底） | **生命周期收尾** ⚠ 见 §3 |
| 4 | `UBattleTransaction` | `Execute` | `BattleTransaction.cpp:36`（`TryExecute`） | **业务本体** |
| 5 | `UBattleTransaction` | `FoldMods` | `BattleTransaction.cpp:35`（`TryExecute`） | **业务本体** |
| 6 | `UBattleTransaction` | `Validate` | `BattleTransaction.cpp:13`（`Start`）与 `:34`（`TryExecute`，**两处**） | **业务本体** |

## 3. 判据：业务本体 vs 生命周期收尾

全表分节只用一把尺子（源自 P3 盘账 ⑩ 的裁决）：

- **业务本体** → **纯虚合理**：引擎不知道子类该干什么，就该逼子类表态。"没想好"是子类的问题，不是基类的问题。
- **生命周期收尾**（销毁 / 退场 / 清理）→ **纯虚是坑**：报应发生在"收场"那一刻，原因却写在子类里，
  现场只剩一句 `LowLevelFatalError`，不好查。

**现存唯一一处收尾类纯虚**：#3 `UnRegisterActivateTiming()`（`EndPlay` 无条件调）。
**已按博士指示忽略（2026-09-16）**——不设计、不施工、不进验收；事实存于 `P3` §7 与 `P3-余项清单` ⑩，
仅供症状回查。若将来新增同类钩子，先回 `01` §6.3 评审。

## 4. 逐基类契约

### 4.1 `USkillComponentBase` —— 技能组件

`Battle/Component/Skill/SkillComponentBase.h`。宿主 = `APlayerState`（技能挂在玩家身上），**全服务器侧**。

**何时该建子类**：每一件具体技能一个子类。这是"技能体"的落点（`09` §5）。
**如何进场**：**不要手动 `NewObject`**——走工厂 `CreateSkill(Owner, SkillTag)`（`SkillComponentBase.h:28`）：
查重 → 从 `FSkillInfo` 取声明 → 取 `SkillClass`（**数据表配置，裸基类进不来**）→ `bDeferred` 创建 →
挂 `ComponentTags` → `RegisterComponent`。Tag 先于 `BeginPlay` 就位是有意为之（时机索引要认它）。
模板版 `CreateSkill<T>` 只是加一层 `Cast`。

| 钩子 | 档 | 职责 | 备注 |
|---|---|---|---|
| `OnCanActivate(Timing, Tx)` | **硬性** | **【就位】**，见下方专段 | `SkillComponentBase.h:51`，纯虚 |
| `RegisterActivateTiming()` | **硬性** | 向 `USkillManagerSubsystem` 登记"本技能听哪些时机" | `:76`；**调用点归你自己**（§7） |
| `UnRegisterActivateTiming()` | **硬性** | 退订 | `:77`；基类 `EndPlay` 兜底调 ⚠ §3 |
| `OnRespond(Tx, Req)` | **可选** | 产出本次响应的修改 | `:66`，默认空体，**空体是合法终态** |

**`OnCanActivate` 的职责 = 【就位】，只三件事**（`09` §6 同文）：

1. **接住接缝**——收下本窗的 `Timing` 与负载 `Tx`。这是技能在窗内拿交易引用的**唯一途径**（`04` §4.1）；
   需要时缓存到成员，供 `OnRespond` 取用。
2. **自判与准备**——决定"这一窗我要不要响、响的话代价与目标是哪个"。只【决定】，不【落修改】。
3. （服务器侧）就位后自持。**表现不在此列**：客户端面板由 UI 订阅 `FClientResponseWindow` 自理（`11` §5.2）。

**纪律（硬性）：不得在 `OnCanActivate` 里提交/放弃。** 提交（`SubmitWindowResponse`）是**回传侧**落点，
在发问钩子里同步调用会把发问与回传两个阶段叠进同一帧，并**抢在客户端收到面板之前落地生效**；
还会触发重入——内层递归可能关窗、甚至立刻开新窗，本层余句随即作废。引擎侧已备**重入守卫**兜底
（`AskNextResponder` 检"本层窗口是否还在"，挡住账本越界写与错位下发），但**那是护栏、不是路**。
"自动生效"的正当写法是**不进询问通道**（`09` §8 契约行：`bAskFirst` 技能进询问通道、全自动直接激活）。

**`OnRespond` 与它的分工，靠默认体写死**：`OnCanActivate` 纯虚（被点名**必须表态**——做了不等于产出）；
`OnRespond` 空体（**应了而不产出是合法情形**，`bAnyResponded` 照记——行为语义而非效果语义，`10` §2）。
两个默认体的不对称**就是分工本身**，不是随手写的。

**样板**：两条测试技能本体未建（`P3` §3.6，`Battle/Abilities/` 空目录）；写法参考 `09` §11 的三个案例。

### 4.2 `UCardComponentBase` —— 卡牌组件

`Battle/Component/Card/CardComponentBase.h`。`UCLASS(..., Abstract)`，宿主 = `AActor`（区域容器属主），
**仅服务器存在、不参与复制**。

**何时该建子类**：每种"有行为差异的牌"一个子类。
**如何进场**：**不要手动 `NewObject`**——走工厂 `Get(Owner, Tag)`（`:31`）：
服务器门控 → 查重（`FindComponentByTag`）→ 取 `UCardManagerSubsystem` → 取表行 →
`bDeferred` 创建 → 挂 `ComponentTags` → `RegisterComponent` → 绑定 `DataGetter` → 写回 `FCardInfo::Card` → 写 `Key`。
**哪一个子类由数据表指定**：`FCardComponentMapping{ Tag, Comp }`（`ArkWarCardTypes.h`），
由 `UCardManagerSubsystem::Initialize` 读进 `FCardInfo::Class`。**引擎侧不 switch 牌名**。

| 钩子 | 档 | 职责 | 调用点 |
|---|---|---|---|
| `Use(Source, Targets, Card)` | **软性** | 使用这张牌的完整逻辑 | `BattlePlayerController.cpp:157`（唯一） |
| `Response(Source, Target, Card)` | **软性** | 打出这张牌响应的逻辑 | **零调用点**（§7） |
| `TrySelectTarget(Source, Target)` | **软性** | 可否被选为目标（默认 `false`） | **零调用点**（§7） |
| `DataConverter(Data)` | **可选** | 把表里非数字的数据串转成整数（默认 `0`） | 经 `FInfoWithData::DataGetter`，在 `GetNumericalDatas()` 里**仅当数据非数字时**执行 |

**软性栏要当回事**：三个虚函数的默认体都是"什么都不做 / 返回 false"，**编译期毫无提示**。
牌"打出去没反应"就是漏覆写 `Use`；"能选中所有人"或"谁都选不中"就是漏覆写 `TrySelectTarget`。

**注意两处**：① `Key` 是 **private 且无 getter**——子类读不到自己的 Tag，需要时自己存一份；
② 自定义析构须调 `Super`——基类析构负责解绑 `DataGetter` 并清 `FCardInfo::Card`（漏调会留悬垂引用）。

**样板**：Source 内**零 C++ 子类**（子类全在数据表指定，尚未建）。

### 4.3 `UGameModeComponentBase` —— 玩法模式组件

`Battle/Component/GameMode/GameModeComponentBase.h`。`UCLASS(..., Abstract)`，宿主 = `AGameModeBase`。
**这一族是"玩法模式"的差异点**（人数、身份分配、选角流程、起手牌数）——换模式 = 换一个子类。

**如何进场**：源码内**无实例化点**（子类经蓝图/关卡放置，`UGameModeComponentBase` 标了
`BlueprintSpawnableComponent`）。取用走静态工厂 `GetCurrentGameMode(WorldContext)`（`:22`，**只查不建、无日志**）。

| 钩子 | 档 | 职责 | 调用点 |
|---|---|---|---|
| `InitCardDeck()` | **硬性** | 开局按玩法与人数组牌堆 | `BattleGameFlowSubsystem.cpp:277` |
| `AllocateIdentity()` | **硬性** | 分配身份；**返回值 = 起始玩家下标** | `:269`，返回值作 `InitPlayers(Start)` 入参 |
| `GetStartCardNum(Asc)` | **硬性** | 该玩家的起手牌数 | `:284`（玩家未实现 ASC 接口时**传 `nullptr`**） |
| `SentSelectOperatorNotify()` | **硬性** | 广播选角通知 | `:274` |
| `CheckOperatorSelection(Player, Op)` | **硬性** | 校验/登记一次选角 | `BattlePlayerState.cpp:131` |
| `ResetOperatorList()` | **硬性** | 重置选角列表 | **零调用点**（§7） |
| `ShouldResetOperatorList()` | **硬性** | 是否需要重置（默认宏体 `return true`） | **零调用点**（§7） |

**`AllocateIdentity` 是唯一"返回值有语义"的钩子**——其余钩子看副作用，它看返回值。漏覆写它不只是崩，
是崩在 `StartGame` 链上（整局的入口）。

**`protected` 三成员是留给你的**：`UnRegisteredPlayers` / `SelectedOperators` / `TotalOperators`。
**基类不初始化、不读写**，全归子类——订阅集合与角色集合是子类实现细节（与技能订阅同精神）。

**样板**：`UDefaultModeComponent`、`UFactionsBattleModeComponent`（各覆写 5 个，**都未覆写
`ResetOperatorList` / `ShouldResetOperatorList`**——因这两个钩子零调用点，见 §7；施工时按需补）。

### 4.4 `UBattleTransaction` —— 交易族

`Battle/Transaction/BattleTransaction.h`。`UCLASS(Abstract)`，普通 `UObject`（非 Actor/组件）。
**交易 = 一次结算的载体**（`04`），族 = 一类结算（移动 / 伤害 / …）。

**何时该建子类**：每一类"结算行为"一个子类。
**如何进场**：`Start()` → 入队 → 子系统 `DriveTransaction` → `Drive()`。**你只管覆写族钩子，不碰驱动器。**

**基类骨架一律非虚、严禁覆写**（`04` §2）：

```
Start()                                   // 服务器门控 + Validate + State 闸门 + 入队
  └─ Drive()                              // 驱动器唯一入口（子系统直调）
       └─ QueryTimings()                  // 落 State=Querying → 按 GetQueryTimingTags 逐扇开窗
            └─ OnWindowClosed()           // 每关一扇推游标、开下一扇；问完 → TryExecute()
                 └─ TryExecute()          // Validate → FoldMods → Execute
                      └─ Finish(bSuccess) // 置 Finished → BroadcastFinish → 通知子系统
```

| 钩子 | 档 | 职责 | 备注 |
|---|---|---|---|
| `Execute()` | **硬性** | **结算主体**：落子/施加效果 | 此时 `FoldMods` 已折过，读折叠后的结果位 |
| `FoldMods()` | **硬性** | **折叠本笔的全部 `ModeRequests`**——一次性消费，与 RPC 到达序无关 | 折叠口径见 `04` §4 |
| `Validate() const` | **硬性** | 入参校验（`Instigator` / `Targets` / 消息） | **两处调用**（`Start` 与 `TryExecute`），须幂等 |
| `BroadcastFinish(bSuccess)` | **硬性** | 收尾广播"A 面事实"（如 `Notify::Card::Moved`） | `04` §8、`12` §5.1 |
| `GetQueryTimingTags()` | **可选** | 登记"在哪些时机被查询" | 默认 `{}` = **直通族**（不开窗直接 `Execute`），零延迟路径 |

**非虚、不得覆写的行为收口**：`AppendModification`（窗口内**唯一**修改入口，只在 `State == Querying` 收）、
`Finish`、`Start`、`Drive`、`QueryTimings`、`OnWindowClosed`（`friend` 给子系统，外部不可调）。

**状态机**（`EState`）：`Spawned → Started → Querying → Executed → Finished`。
`AppendModification` 的状态闸门就是 `Querying`——**窗外提交一律静默拒绝**，这是锁之外的第二道闸门。

**样板**：`UCardMoveTransaction`（`Transaction/SubTransaction/`）——覆写全 5 个，
外加一个**结构干预点** `ModifyMessage(TFunctionRef<void(FMoveMessage&)>)` 供窗口内改移动结构，
内带两条纪律守卫（`_Count` 只走 ModRequest 折叠通道；预置牌锁定 `_From`）。**新族照此形状写。**

### 4.5 接口族

接口与基类不同：**你实现接口，不是继承接口**——在类声明上加 `public IXXXInterface`（多继承），
并在 `.cpp` 里实现全部纯虚（§2.2 表）。**接口没有钩子职责表**，因为接口函数就是普通 API，
"何时被谁调"归各自的调用方（见 `12` 与各卷）。

注意 `UCLASS` 与 `UINTERFACE` 的写法差异：`IXXXInterface` 类内只有函数，**不写 `GENERATED_BODY()` 之外的宏**；
蓝图暴露需要额外的 `BlueprintNativeEvent` + `Execute_` 包装（`UCardManagementBusComponent` 未走这条，
全部是 C++ 侧调用）。

## 5. 跨基类通用纪律

1. **服务器权威**：所有钩子只在服务器侧有真实调用（门控散在各入口：`IsRunningOnServer` / `HasAuthority` /
   `GetNetMode`）。子类**不需要**再自己判一次网络模式，但**不得**假设钩子会在客户端被调。
2. **不得在"发问/将发生"类钩子里做"已发生"的事**：`OnCanActivate` / `GetQueryTimingTags` / 窗口内钩子
   属于 B 面（将发生、可干预），产出的效果只能经**唯一收口**（`AppendModification` / `ModifyMessage`）
   落到交易上，不能直写结果位（`ArkWarDelegates.h` 顶部的通知面宪法）。
3. **重入要当心**：引擎的关窗/收尾是**同步**的（`CloseTimingWindow` 会立刻回调持有者，回调可能开新窗）。
   钩子里做"推进"类动作（提交/放弃/入队/嵌套）会把两个阶段叠进同一帧。发问侧已有守卫兜底（§4.1），
   但**别依赖护栏**。
4. **日志英文**、失败要留痕：警告用 `UE_LOG(..., Warning, ...)`，格式随各族既有前缀
   （`[GameFlow][...]` / `[USkillComponentBase][...]` / `[UCardComponentBase][...]`）。
5. **缺省即静默**：软性钩子的默认体"什么都不做"，不会有任何提示。**该覆写的没覆写，症状是行为缺失，
   不是崩溃**——排查时先对本表核一遍档位。

## 6. 新建一个子类的核对表

- [ ] **选基类**：属于哪一族（技能 / 卡牌 / 玩法模式 / 交易 / 接口）？
- [ ] **填硬性**：§2.1 该基类的全部 `PURE_VIRTUAL` 是否都覆写？**漏一个就是一颗定时炸弹**（§2.1 表查崩点）
- [ ] **判软性**：§4 该基类的"软性"栏，默认体在本子类语义下是否够用？不够就覆写
- [ ] **读纪律**：§4 该基类的"纪律"段（尤其 §4.1 的"不得在 `OnCanActivate` 里提交"）
- [ ] **走工厂**：用基类的静态工厂进场（`CreateSkill` / `Get` / 子类自选挂载点），**不手动 `NewObject`**
- [ ] **配数据**：子类如何被选中（技能/卡的 `SkillClass` / `FCardComponentMapping`；模式组件靠放置）——
      操作员/卡的映射表填了吗？
- [ ] **记日志**：关键路径留英文日志；失败分支要有告警，别静默 `return`
- [ ] **想重入**：钩子里会不会触发推进（提交/放弃/入队/嵌套）？会的话回 §5.3
- [ ] **编译**：新增 `.cpp` 会被 Adaptive Build 踢出 unity 单独编译——**include 债藏不住**，一次编过才算数

## 7. 现状台账：零调用点的钩子（**不是缺陷**）

以下钩子/接口**当前零调用点或零实现**，是"框架已交、使用者未到"的既定状态，**不是缺陷、不列待办**
（盘于 2026-09-17，`P3` 盘账口径）：

| 项 | 状态 | 说明 |
|---|---|---|
| `RegisterActivateTiming()` | 零调用点 | **基类 `BeginPlay` 刻意不代调**——挂载点归子类自选（覆写 `BeginPlay` / 构造 / 首次使用）。已定稿口径（`P3` §3.3.1） |
| `UCardComponentBase::Response` | 零调用点 | 相邻的 `Server_Response` 亦为空体，随出牌响应链落 |
| `UCardComponentBase::TrySelectTarget` | 零调用点 | 随目标选择 UI（`05`）落 |
| `UGameModeComponentBase::ResetOperatorList` / `ShouldResetOperatorList` | 零调用点 | 两个现成子类均未覆写——因零调用点，故未爆 |
| `IUpgradeableSkillInterface` | 零实现 | 技能演化未落地（`09` §7，P6） |
| `UCardComponentBase::DataConverter` | 有绑定点、条件执行 | 仅当表数据**非数字**时经 `DataGetter` 执行；默认返 0 |

> **判据**：零调用点 ≠ 缺陷。缺陷是"**有调用点、但调用点上的行为不对**"。
> 本表存在的意义是：写子类时别被"这个钩子好像没人调"误导成"不用覆写"——**调用点会随对应阶段长出来**，
> 而硬性钩子一旦长出来就是崩点。
