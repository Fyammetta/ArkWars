# 12 事件与委托总表

> 跨卷登记册：把"**谁在什么时候广播什么、谁订阅、怎么登记**"集中成一张可对账的表，避免事件定义散落在 `02`/`03`/`04`/`08`/`10` 各卷。
> 本卷**不改任何卷的语义**，只登记形状与时机；委托与事件类型的**权威定义**在本卷 §附录（现行部分逐字于 `ArkWars/Battle/Toolkits/ArkWarDelegates.h` 与 `Battle/Transaction/EventTypes.h`）。
> 触发问题背景：`03` 只说"两条通道"，`10` 只说"窗口策略"，`04` 只说"交易生命周期"——但**没有一处回答**"事实通知有哪些委托、谁在何时广播""ModRequest 是怎么被通知加入的""交易执行中怎么插入另一笔交易"。本卷补这三件事。

## 1. 职责边界

| 管 | 不管 |
|---|---|
| 事件清单：名称、通道归属、委托/负载形状 | 事件被订阅后用于什么规则（各卷） |
| **广播者**（哪个类/哪个函数）与**广播时机**（哪个状态落定之后） | 窗口策略与询问次序（`10`） |
| **订阅者**与**订阅登记方式**（委托绑定 / 时机索引 / 钩子覆写） | 交易落子细节（`04`）、容器写接口（`08`） |
| 新增事件时的登记纪律（先答"是否已事实化"，`03` §2） | 客户端表现与复制（`11`） |

## 2. 三个通知面（本卷的分类口径）

系统里所有"通知"归三个面，**绝不混用**（`03` §2 的第一原则在本卷落到具体面）：

| 面 | 含义 | 载体 | 谁能干预 | 本卷小节 |
|---|---|---|---|---|
| **A 事实通知面** | 事情**已发生** | 同步多播委托（现有 `ArkWarDelegates.h`）+ 复制 OnRep | ❌ 只读反应 | §3 |
| **B 查询通知面** | 事情**将发生** | 响应窗口（`OpenTimingWindow` + `Responders` + 负载） | ✅ 改/防/替代/追加 | §4 |
| **C 生命周期通知面** | 引擎**内部推进** | 直调钩子（`BroadcastFinish` / `OnWindowClosed` / `OnTransactionFinished`） | ❌（引擎私有） | §5 |

- A 面是"给外部订阅的事件"；C 面是"引擎内部链路"，**默认不可订阅**——外部要观察交易/窗口必须经 §5.2 的事件化委托，不得直接挂钩子。
- B 面的"通知"不是委托，而是**窗口开启 + 逐个询问**；响应者对负载的修改经唯一入口 `AppendModification`（§4.3）。

## 4. B 面：查询通知链路（**ModRequest 是怎么被通知加入的**）

### 4.1 链路总览（仅服务器）

```
创建方 Start() → EnqueueTransaction(Tx) → 驱动 DriveTransaction()
  → Tx->QueryTimings()                             ← P3 已落（开窗链入口：置 Querying → 逐个开窗）
      → OpenTimingWindow(TimingTag, Tx, Policy)     ← 唯一开窗入口（03 §4 / P3 §3.2）
          ① 查时机索引（SkillManager）得候选技能
          ② 合法预检（在场/可用/账本，P6 前常量放行）
          ③ 填 Responders 名单（FResponseEntry）
          ④ 名单填出后广播 FWindowOpened（新增，§5.2）  ← "通知"发生点
             （入口另设 `IsResponding()` 前置检查，只查不置位：响应中 → 拒绝 + 日志，卷 10 §4）
          ④' 空名单（无监听者）→ 立即关窗返回，**不上锁**（零延迟直通，P3 §3.5/§7）
          ⑤ `TryEnterResponseLock()` 单一进入收口（锁本体只在此与 `ExitResponseLock` 内改写）：
             成功 → `bRespondingLock = true` + 旁路广播 `FResponseLockChanged(true)`；
             已在响应中 → 返回 false 且不重复广播（理论不可达，前置检查已拦）
             → 按策略逐个询问（下发候选，附 Timeout 时间预算，10 §5）
               └ 关闭时机统一只通过 UI 决定：UI 倒计时到点 → 直接请求关闭（= 放弃，同一 RPC 入口；引擎侧无定时器）
               └ 响应者（技能体）从窗口负载拿到 Tx（03 §4：负载 = 交易引用）
                    └ Tx->AppendModification(Req)   ← ★ ModRequest 在此加入（唯一入口）
                         └ 广播 FTransactionModified（新增，§5.2；仅日志/表现，不参与折叠）
               └ 或放弃
          ⑥ 汇总 → Close → 广播 FWindowClosed（新增）→ 回调持有者
      → OnWindowClosed()：汇总结果 → 被防/无效 Finish(false) / 否则 Execute()
  → Execute()：FoldMods() 一次性消费 ModeRequests → 回填结果位 → 落子 → Finish(true/false)
```

**结论（回答"ModRequest 怎么被通知加入"）**：ModRequest **不是被"推送"进交易的**，而是：

1. 交易在 `QueryTimings()` 里**开窗**，窗口开启时**广播 `FWindowOpened` 并逐个询问**响应者（这才是"通知"）；
2. 响应者（技能体）被通知后，从**窗口负载**（= 交易引用 `Tx`）拿到交易，**主动**调 `Tx->AppendModification(Req)`；
3. 交易侧只有**唯一收口** `AppendModification`（`State == Querying` 才收，追加不覆盖，见 §4.3）。

**现状（P3 窗口链已落）**：`QueryTimings()` 置 `Querying` 后按族登记的查询时机经 `OpenTimingWindow` 开窗，逐人询问收 `AppendModification`（广播 `FTransactionModified`），关窗回调 `OnWindowClosed` 续走——"通知链路"整段已通，名单侧 `CollectResponders` 也已接索引（查表 → 验活预检 → `Priority` 降序 × 座次排序）。唯一空转处在上游：技能子类订退内容未填 → 索引无写入方 → 查表恒空走"无监听直通"（该项归技能子类，P3 只交钩子框架、非 P3 余项）；候选下发/提交 RPC 仍待 P3 余项（`P3` §3.3/§3.8、`P3-架构图集` §2/§6）。

### 4.2 响应者"怎么知道自己该响应"（两种登记方式）

| 方式 | 谁登记 | 索引 | 适用 |
|---|---|---|---|
| **声明式**（主流） | 技能声明 `ListenTimings`（`09` §4） | `USkillManagerSubsystem` 建"时机 → 技能"索引（`03` §5），开窗查表 | 技能响应（`09`） |
| **指令式** | 开窗方直接构造 `Responders` | 无索引 | 阶段窗口、调试/测试 |

- 候选只表示"这个时机有技能在听"，是否真唤醒由 `10` 的策略（`Priority` 降序 × 座次序 + 逐人询问/自动激活；`All`/`FirstOnly` 同时发生无序）决定。
- **名单排序（现码已落，`P3` §3.3.2）**：候选排序 = `Priority` 降序为主键（技能登记时带入 `FSkillListenerEntry::Priority`）× 座次为次序（从当前回合玩家起升序轮转，`CollectResponders` 开窗现算），平手由 `StableSort` 保注册序、非法座位沉底。`10` §2 原文"不设技能级 `ResponsePriority`"已按现码更新。
- 事实通知侧（A 面）**不需要索引**：走委托绑定或 `GameplayEvent` 广播订阅。

### 4.3 `AppendModification` 的约束（`04` §4.1 的收口）

- **唯一入口**：响应者只能追加 `FTransactionModRequest`，不直写结果位、不覆盖共享值。
- **数值/被防的唯一通道，结构位不经此处**：`FTransactionModRequest` 的四类 Op 全是数值语义（`04` §4），**不新增结构类 Op**；目标/发起者/族意图位的结构修改 = 窗内直写公开字段与族级受控干预点（`GetMessage()`/`ModifyMessage()`，`04` §4.1 通道分工），本入口不扩形状。
- **窗口期限定**：`State == Querying` 之外一律丢弃（现行实现即此语义）；族干预点 `ModifyMessage` 同款闸门。
- **服务器限定**：客户端不驱动交易（`04` §3），故追加只发生在服务器。
- **顺序无关**：折叠对数组插入序不敏感（同 Op 可交换、跨 Op 族序固定），"不按 ServerRPC 到达序"由折叠器保证（`10` §2）。
- **可观察**：追加时广播 `FTransactionModified`（§5.2），供日志/表现/回放核对——**广播失败不影响折叠**。

## 5. C 面：生命周期通知与事件化

### 5.1 现状（内部链路，非外部事件）

| 环节 | 现行实现 | 可订阅性 |
|---|---|---|
| 交易入队 | `UBattleTransaction::Start()` → `System->EnqueueTransaction(this)`（**直调**） | ❌ |
| 交易收尾 | `UBattleTransaction::Finish()` → 族钩子 `BroadcastFinish(bSuccess)` → `System->OnTransactionFinished(this)`（**直调**） | ❌ |
| 窗口开/关 | `OpenTimingWindow` → 逐个询问 → `CloseTimingWindow`（**直调**；外部观察点 = §5.2 的 `FWindowOpened/Closed`） | ❌ |
| 嵌套进出 | 已落（2026-09-16）：`PushNestedTransaction`/`PopNestedTransaction` + `OnTransactionFinished` 栈顶判定（**直调**；`FTransactionNested` 广播点未接，§5.2） | ❌ |

> 族钩子 `BroadcastFinish` 是**族自己的事实广播位**（`04` §2：`true` → `Card.Moved`/`Damage.Applied`，`false` → `Damage.Prevented`）。`UCardMoveTransaction::BroadcastFinish` 已真广播——成功落子经 `UBattleGameFlowSubsystem::OnCardMoved` 发出 `Notify::Card::Moved`（负载 = 双端 Actor + 本次实际移动的 `Cards`，委托定义见 §3.1/附录 A）；`false` 路径本族无对应标签，**不广播**（`MovedIn`/`MovedOut` 细拆保留待用）。伤害族（P4）按同形落地。

### 5.2 目标形态：内部链路事件化（新增委托，定义见 §附录 B）

> 口径：**只增观察点，不改推进语义**——广播是"旁路"，任何订阅者异常都不得影响交易/窗口推进（§7 契约）。落地位置建议 `ArkWarDelegates.h`（需前置声明 `UBattleTransaction`/`FResponseWindow`/`FTransactionModRequest`）。

| 委托 | 广播者 | 广播时机 | 订阅者（典型） |
|---|---|---|---|
| `FTransactionEnqueuedDelegate`（Tx） | `UBattleGameFlowSubsystem::EnqueueTransaction` | `PendingTransactions.Add(Tx)` 之后、忙锁分支之前 | 表现队列、日志、调试面板 |
| `FTransactionFinishedDelegate`（Tx, bSuccess） | `UBattleGameFlowSubsystem::OnTransactionFinished` | 校验 `Tx == ActiveTransaction` 通过、清 `ActiveTransaction` 之前 | 账本对账、表现、调试 |
| `FTransactionNestedDelegate`（Child, Parent） | `UBattleGameFlowSubsystem::PushNestedTransaction` / `PopNestedTransaction` | 入栈后 / 出栈后 | 表现（"打断"提示）、调试 |
| `FWindowOpenedDelegate`（Window） | 窗口管理器 `OpenTimingWindow` | `Responders` 填出后、开始询问前 | 表现、日志、调试（**服务器侧**；客户端 UI 的候选不经此委托，见 §5.2 末尾注） |
| `FWindowClosedDelegate`（Window, bAnyResponded） | 窗口管理器 `Close` | 结果回写完成后、回调持有者前 | 阶段机（调试）、表现 |
| `FResponseLockChangedDelegate`（bResponding） | `UBattleGameFlowSubsystem::TryEnterResponseLock` / `ExitResponseLock` | 锁切换瞬间（开窗入锁 / 关窗撤锁），bool 形参为新值 | UI 状态镜像、日志、调试面板 |
| `FTransactionModifiedDelegate`（Tx, Req） | `UBattleTransaction::AppendModification` | `ModeRequests.Add(Req)` 之后 | 日志、表现、回放 |

> **接线注意（2026-09-16，⑤ 施工前实测）**：余下三条的开头两条各有坑，接线前先读——
> ① **实例名不得与成员函数同名**：`UBattleGameFlowSubsystem` 已有成员函数 `OnTransactionFinished(UBattleTransaction*)`（`.h:117`），
>    委托实例若同名，类作用域内数据成员与成员函数冲突 → 编译错。建议实例名取 `TransactionFinished`（或 `OnTransactionFinishedNotify`）——
>    上表"广播者"一栏记的是**函数**，不是实例名；三条实例统一加在 `.h:158-161` 那组之后（服务器侧观察位）。
> ② **`bSuccess` 现无通路**：收尾钩子 `UBattleGameFlowSubsystem::OnTransactionFinished(Tx)`（`.h:117` / `.cpp:325`）**不收成功位**，
>    且 `UBattleTransaction` **不存结果位**（`Finish(bool)` 把 `bSuccess` 交给族钩子 `BroadcastFinish` 后即丢，`BattleTransaction.cpp:57-66`）——
>    要接这条两参广播，须把成功位透传进收尾钩子（三处同改：`.h:117`、`.cpp:325`、`BattleTransaction.cpp:65`），
>    或在交易上落一个结果位成员（与"结果位见 `04` §4"口径并用时取后者亦通，但多一份状态账）。
> ③ 嵌套那条（`FTransactionNested`）随 `04` §3.2 嵌套落地，本阶段只留声明。

> 注意：`FWindowOpened/Closed` 是**服务器侧**观察点；客户端 UI 的候选下发**不走属性复制**，而是
> **ClientRPC 点对点**下发的扁平 DTO（形状与四条理由见 `11` §5.1/§5.2），不经这两个委托。
> 三处"复制"误读一并澄清：① 窗口本体（`FResponseWindow`）住在 `UWorldSubsystem` 的 `TOptional` 里——
> 无复制载体，且含 `TStrongObjectPtr`（不可序列化）；② 交易是裸 `UObject`（`04` §2），不参与复制；
> ③ C 面委托只在服务器广播，**客户端一个都不订阅**（`11` §3）。

## 6. 交易中插入交易（事件序）

机制本体在 `04` §3.2（**排队** vs **嵌套插队**），本卷只登记**外部可观察的事件序**：

```
普通入队（不打断）：
  Parent.Execute 中 → Enqueue(Child)
     → FTransactionEnqueued(Child)          （Parent 仍 Active）
     → Parent.Finish(true/false) → FTransactionFinished(Parent)
     → DriveTransaction() → Child 执行 → FTransactionFinished(Child)

嵌套插队（打断，唯一插队口）：
  Parent 边界（OnWindowClosed / Execute 入口）→ PushNested(Child)
     → FTransactionNested(Child, Parent)    （Parent 挂起，改由 NestedStack 帧强持有）
     → Child 完整结算 → FTransactionFinished(Child)
     → PopNested → 恢复 Parent（**不重发 Enqueued、不重入队**）
     → Parent 继续 → FTransactionFinished(Parent)
```

- 外部看到的事件序 = `Nested(Child,Parent)` → `Finished(Child)` → `Finished(Parent)`；**同一时刻只有一个 ActiveTransaction** 的观察不因嵌套改变。
- 嵌套**只能在交易边界发起**（窗口回调内 / `Execute` 入口），不允许在落子中途挂起 `Execute`——理由与约束见 `04` §3.2。

## 8. 扩展点

新增一个"事实事件"（三步，不碰引擎主干）：

事件化 vs 直调的选择：

- 外部需要观察 → 用委托（A/C 面事件化）；
- 引擎内部推进 → 保持直调（`OnTransactionFinished` 等），**不为"优雅"把内部链路改成委托**——回调顺序与失败语义会被订阅者污染。

## 10. 案例（仅作样本，不进框架）

- **阶段跳过 vs 阶段订阅**：订阅 `FGamePhaseChangeDelegate` 只能"知道阶段变了"（A 面，不可否决）；要"进入判定前跳过"必须开 `Judgement_Pre` 窗口（B 面）。同一事实两通道对照样本。
- **伤害减免的 ModRequest 全程**：`UDamageTransaction` 开 `Damage.Incoming` 窗（`FWindowOpened`）→ 技能体拿 `Tx` 追加 `{Op=Clamp, 1}`（`FTransactionModified` 日志可见）→ 关窗（`FWindowClosed`）→ `OnWindowClosed` 走 `Execute` → `FoldMods` 收敛 → `Finish(true)`（`FTransactionFinished`）。样本用途：验证 §4 通知链路端到端可观察。
- **濒死打断当前结算**：伤害交易在"落子前边界"发起 `PushNestedTransaction(DyingTx)`（`FTransactionNested`）→ 濒死交易完整结算（救回/淘汰）→ `PopNested` 恢复伤害交易。样本用途：验证 §6 事件序与 `04` §3.2 嵌套语义（P5 验证）。
- **发牌守恒对账**：订阅 `FTransactionFinished`，对每笔 `UCardMoveTransaction` 记账，一局结束核对全局卡牌总数（`00-路线图` §4 守恒贯穿线）。

```cpp

#include "GameplayTagContainer.h"

class UBattleTransaction;

enum class EWindowPolicy
{
	All,
	InOrder,
	FirstOnly
};


struct FTransactionModRequest
{
	enum class EModOp : uint8 { Override, Add, Multiply, Clamp };	// 旧稿为 Ignore，P3 已改（"免疫/被防" = 折零表达，定稿 (a) 2026-09-16）

	EModOp Operation;

	float Magnitude;

	TWeakObjectPtr<APlayerState> Actor;

	int32 Priority;
};


// 窗口内一条可响应项：时机索引给出的合法监听者快照（技能标识 / 所属玩家 / 登记优先级）。
// 不携带交易引用——名单与负载无关，负载只挂在窗口上（单一事实来源；候选下发也只用到 Key/Owner）
struct FResponseEntry
{
	int32 Priority;

	TWeakObjectPtr<APlayerState> Owner;

	FGameplayTag Key;
};

// 窗口基座（纯 server 私产，无复制语义，故为普通结构体）
struct FResponseWindow
{
	FGameplayTag Timing;

	// 负载本体 + 悬停期强持有：交易出队后 PendingTransactions 不再持有它，
	// 这里是窗口悬停期唯一的 GC 锚（不依赖反射追踪）；纯阶段时机为空
	TStrongObjectPtr<UBattleTransaction> Tx;

	TArray<FResponseEntry> Responders;

	float Timeout;
};
```

> **与 `03` 附录（设计目标形态）的命名差异**（`03` §8 已记）：
>
> | 字段 | `03` 附录（设计） | 代码现状（本附录 C） |
> |---|---|---|
> | 窗口时机 | `TimingTag` | `Timing` |
> | 响应者技能标识 | `SkillTag` | `Key` |
> | 交易引用持有（窗口） | `TObjectPtr<UBattleTransaction>` | `TStrongObjectPtr<UBattleTransaction>`（悬停期 GC 锚，非反射追踪） |
> | 交易引用持有（响应者条目） | 条目自带 `Tx`（`UBattleTransaction*`） | **无此字段**——名单与负载解耦，负载只挂窗口（2026-09-16 定稿） |
> | 响应者条目类型名 | `FResponderEntry` | `FResponseEntry` |
>
> **命名以代码为准**（`FResponseEntry`/`Timing`/`Key`）。交易引用的持有按"在飞集合"分三处锚
> （`04` §3.2 不变量 1 锚点规则）：`ActiveTransaction`（`UPROPERTY() TObjectPtr`，当前结算者，
> 强持有 + 反射可见）、窗口 `Tx`（`TStrongObjectPtr`，悬停期）、嵌套栈帧两字段（`TStrongObjectPtr`，
> 挂起期）。**三处都是强引用**——任一时刻在飞的交易至少被其一持有，生命周期不寄在"窗口开着"上
> （交易在无窗口的同步段同样在飞）。

### D. 嵌套栈类型（`04` §3.2，2026-09-16 已落）

```cpp
// 嵌套栈帧：一笔被挂起的父交易 + 正在结算的子交易（04 §3.2）
// 两字段必须同为强引用（TStrongObjectPtr）：换手后 ActiveTransaction 指向子，
// 父的强引用只剩本帧——写 TWeakObjectPtr 会让父在子交易悬停期被 GC，出栈时直接拿到悬空指针
// （04 §3.2 不变量 1 锚点规则）
struct FNestedTransactionFrame
{
	FNestedTransactionFrame() = default;
	FNestedTransactionFrame(UBattleTransaction* InParent, UBattleTransaction* InChild)
		: Parent(InParent), Child(InChild) {}      // 显式构造：TStrongObjectPtr 的裸指针构造是 explicit，聚合花括号初始化会被拦下

	TStrongObjectPtr<UBattleTransaction> Parent;   // 被挂起的父交易（挂起态，由本帧强持有）
	TStrongObjectPtr<UBattleTransaction> Child;    // 正在结算的子交易（与 ActiveTransaction 双重锚）
};

// 载体（UBattleGameFlowSubsystem，04 §3.2）：
TArray<FNestedTransactionFrame> NestedStack;     // 嵌套栈（无深度上限成员：上限只作设计约定，04 §3.2 不变量 2）
```

> **现状（2026-09-16 更新）**：本类型与 `NestedStack` 字段**已落地**——`PushNestedTransaction`（门控 +
