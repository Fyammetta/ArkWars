#### 3.3.1 发现：时机索引——为什么技能组件不能自己订阅时机

窗口的询问是一门有程序的生意，四件事缺一不可，而委托订阅表一件都给不了：

| 窗口需要 | 自订阅委托给不了的原因 |
|---|---|
| **排序名单**（谁先被问是玩法本身） | 多播委托调用序 = 注册序；注册序取决于组件谁先 `BeginPlay`——把玩法次序押在初始化时序上不可接受 |
| **问前预检**（不合格的不进名单） | 委托是"广播到即被调"，没有"先筛再问"这一拍 |
| **逐人询问**（`InOrder` 一次只问一人、悬停等 RPC） | 广播是一口气全放，节奏无法攥在窗口手里 |
| **容忍退场**（技能组件中途销毁） | 忘退订 = 悬垂回调；索引持弱引用、开窗时逐个验活，死掉的天然出局 |

所以 `USkillManagerSubsystem` 建**时机 → 监听技能**索引（形状施工时定，语义如下）：

```cpp
// 键 = Event.Timing.* 标签；值 = 在听这个时机的技能条目（形状已落：USkillManagerSubsystem::SkillTimings）
TMap<FGameplayTag, TArray<FSkillListenerEntry>> SkillTimings;
// FSkillListenerEntry（ArkWarSkillTypes.h）= { TWeakObjectPtr<USkillComponentBase> Skill,
//   TWeakObjectPtr<APlayerState> Owner, int32 Priority = 0 } + IsValid()（两者俱活）/ operator==（只比 Skill）
// 登记册只存"关系"，刻意不存两样原料，一律开庭现取：
//   Key      —— 权威在组件（USkillComponentBase 持有 FSkillInfo，取用走 GetSkillTag()；
//               CreateSkill 已把技能 Tag 挂上 ComponentTags 供 FindComponentByTag 反查）
//   座次     —— 局内活状态，实时读 PhaseComponent（§3.3.2）
// Priority 是例外：技能级排序主键（降序），登记时由技能侧带入、随条目一起存——
//   座次是局面属性（换座会变，必须现算），优先级是技能属性（登记即定，无须现算）
// 组件已死的条目整个作废（验活出局；RegisterSkillTiming 的 Entry.IsValid() 即第一道关），
// 不存在"需要 Key 而组件不在"的场合——故 Key 无须副本
// 订/退通道：技能子类实现 RegisterActivateTiming()/UnRegisterActivateTiming()（均纯虚），
// 钩子内容 = 调本子系统的 RegisterSkillTiming/UnregisterSkillTiming（听哪些时机的决定权在子类；
// 订阅调用点也归子类自选，退订由基类 EndPlay 兜底回调）
```

**订阅内容归子类，基类不做限制**：`USkillComponentBase` 只做宿主（把 `FSkillInfo::SkillClass` 实例化到 PlayerState，见 `09` §6）与两个钩子——`RegisterActivateTiming()`（订）/ `UnRegisterActivateTiming()`（退），两者纯虚、内容全归子类。**基类不规定听哪些时机、不规定订阅时机、也不检查订没订**；子类在钩子里经 `UBattleFunctionLibrary::GetSkillManager(Owner)` 拿 `USkillManagerSubsystem`，直调 `RegisterSkillTiming` / `UnregisterSkillTiming`：

- **订阅集合自由**：一件技能组件听 0~N 个时机（钩子留空 = 不订阅），中途改集合也合法；集合是子类实现细节，**不上升为基类/声明数据的字段**（`FSkillInfo` 不新增"监听时机表"，引擎不替子类读它）；
- **订阅调用点自选**：基类 `BeginPlay` 保持空实现、**不代调** `RegisterActivateTiming()`——子类自选挂载点（覆写 `BeginPlay` / 构造 / 首次使用 / 按需增删），基类不催也不检查（该钩子全项目尚无调用方——框架已交，调用方属子类施工，不列本阶段清单）；
- **退订由基类兜底**：`EndPlay` 回调 `UnRegisterActivateTiming()`，不依赖子类记性；即便子类提前自退、中途销毁或换形态，索引侧最多留个弱引用，开窗时验活出局（§3.3.3），不会悬垂。

**宿主侧顺序**（`CreateSkill` 已定）：打 `ComponentTags`（技能 Tag）→ 写成员 `SkillInfo`（`GetSkillTag()` 的来源）→ 延迟注册 → `RegisterComponent` 触发 `BeginPlay`——保证子类钩子里 `GetSkillTag()` / 声明 / 索引都已就位。
订阅完，"何时被问、第几个被问、有没有资格被问"全由窗口按策略裁决——组件只管"听了什么"，不管"何时被调用"。

> **现状（P3 §3.3.1）**：索引本体已落——`SkillTimings` + `RegisterSkillTiming`（门控 + 验活 + 查重）/ `UnregisterSkillTiming`（门控 + 空指针校验 + 销账查无此人告警）/ `GetSkillListeners`（门控 + 按值返回快照，遍历期源表可增删）；注册表填充侧 `OnAllOperatorSelected`（按本局选中的 operator 从 `FSkillComponentMapping`/`FOperatorSkillInfo` 两张数据表批量填 `SkillMapping`）与 `AppendSkill`（按 Tag 单条追加）已落。宿主侧 `CreateSkill` 工厂（查重 → `GetCurrentSkillByTag` 取声明 → 写 `SkillInfo` → `bDeferred` 注册 → 挂 `ComponentTags`）、`GetSkillTag()`（读成员 `SkillInfo`）、`OnCanActivate()` 钩子、订/退钩子 `RegisterActivateTiming()` / `UnRegisterActivateTiming()`（均纯虚）已声明；`EndPlay` 已回调 `UnRegisterActivateTiming()`、`BeginPlay` 为空实现；名单侧 `CollectResponders` 已接索引（§3.3.5）。**框架已闭合**——P3 的交付到"两个纯虚钩子 + 基类 `EndPlay` 回调"为止，**子类填什么、何时订、有没有订，均不属本阶段**（随技能子类施工，`P6` §5）。由此有两个当前态（均非缺陷、不列待办）：① 无子类 → 索引无写入方 → 查表恒空、每窗仍走"无监听直通"；② `RegisterActivateTiming()` 全项目尚无调用方（基类不代调，挂载点归子类自选）。另有一条子类接入时的坑：③ `UnRegisterActivateTiming()` 纯虚却被 `EndPlay` 无条件调用，子类漏覆写即 `LowLevelFatalError`（§7）。

**查表成本**：索引空表 = 直通（§7），绝大多数移动窗走这条零延迟路径；这也是"无监听直通优先于整点全开"的底气。

#### 3.3.2 排序：`Priority` 降序 × 座次（开窗实时读取）

**名单排序 = 登记优先级降序为主键，座次为次序**（`CollectResponders` 现行实现，`10` §2）：
`Priority` 是**技能属性**（`FSkillListenerEntry::Priority`，登记时由技能侧带入、随条目存）；座次是**局面的属性**（同一门技能，坐的位置不同、当庄的人不同，被问的先后就不同）——故一个存、一个开庭现算：

- **主键 `Priority` 降序**：登记优先级高的先被问；只有 `Priority` 相同才比座次；
- **次序 = 座次轮转**：从**当前回合玩家**起，按 `PlayersInOrder` 的下标升序轮转——`(Index - CurPlayer + PlayerCount) % PlayerCount`。座次不是数组裸下标，是**以行动者为起点的相对序**：同一份名单，换人当庄，询问序整体轮转。`FResponseEntry.Priority` = 登记优先级快照（供 UI 显示/日志）；
- **平手保注册序**：两键皆相同（同优先级且同座）由 `StableSort` 保持原序 = **注册稳定序**——注册序**不承载玩法语义**，唯一职责是确定性（同局面收敛可复现，回放对账，`11` §7）；
- **非法座位沉底**：响应者不在座次表（`GetPlayerIndex(Owner)` 返回 `INDEX_NONE`）、或座次表未就绪（`GetPlayerCount() <= 0`）时，座次键取 `PlayerCount`（最大）→ 排到最后、不参与轮转（"宁空勿乱"，座次缺失不猜序）；
- **`All` / `FirstOnly`**：**无序**——现实层面同时发生，各自独立决定 / 首响生效，名单只是有权者集合（排序照跑，只是策略不消费次序）。
- **本轮先做升序轮转**：`10` §2 提到的方向规则（`ISeatLayout`，顺/逆时针可配）**未落**，现码只有"从当前玩家起升序"一种（§7）。

> **实现注记（易踩坑）**：必须 `StableSort`——`TArray::Sort`（introsort）不稳定，会吃掉"平手保注册序"的承诺；比较器须守严格弱序（相等返回 `false`，禁用 `<=`），否则 introsort 可能越界。

**座次的唯一权威 = `UGamePhaseManagerComponent` 的 `PlayersInOrder` + `ActivePlayerIndex`（旋转起点）**，
且必须**开窗那一刻实时读取、现场计算**——索引与任何登记数据**不存座次快照**：

- 理由：存在调换座次类效果（换座/易位），座次是局内活状态。若登记快照，换座技能就要挨家挨户改副本，
  漏改一处 = 询问序静默错一轮，且名单看着齐整、极难验尸；
- 实时读取让换座效果的实现成本归零：它只改 `PhaseComponent` 那一份权威，下一扇窗自动用新座次，全系统没有第二份座次需要对账；
- 实现材料是现成的：`UBattleGameFlowSubsystem` 自带 `GetPhaseManager()` / `GetPlayerIndex(Player)`；两字段均为复制字段，客户端 UI 显示"等待谁响应"与服务端名单序天然同源。

**快照时刻 = 开窗填出 `Responders` 之时**（窗内冻结、窗外实时）：名单与次序自此冻结，本窗按它问到底；
悬停期发生换座**不影响进行中的窗**（中途改序 = 开庭换法官），新座次自下一窗生效。
悬停期玩家**离场**不适用本条——那是失效传播（`10` §3，P7）的地界。

#### 3.3.3 预检：进名单前的资格审查

候选只表示"这个时机有技能在听"，入名单前逐个过闸（`10` §4）：

- **来源在场**：所属玩家在场且未出局（弱引用验活在此一并做）；
- **技能可用**：组件存活、未被封印（封印类状态效果属 P7，P3 只验存活）；
- **账本余量**：频率/代价可付（`07`）——**P6 前常量放行**，代码留占位注释。

预检不过 = 不进名单，**有日志**（自动方也过同一道预检，`10` §4）。

#### 3.3.4 询问：InOrder 最小流程（与现行实现的对照表）

| 步骤 | 落点函数 | 做什么 |
|---|---|---|
| 开窗 | `OpenTimingWindow` | 门控 → 单层保护 → **前置 `IsResponding()` 检查**（响应中 → 拒绝 + 日志，不触碰任何状态、不开窗）→ `CollectResponders`（§3.3.1–3）→ 广播 `FWindowOpened` → 空名单直通关窗（不上锁）/ **正式入锁 `TryEnterResponseLock()`** + 广播 `FResponseLockChanged` → 进询问 |
| 逐人问 | `AskNextResponder` | 游标有效 → 给 `Responders[游标].Owner` 的客户端下发"你有响应权 + 候选"（附 `Timeout` 时间预算）→ **返回**（引擎不等待，推进纯事件驱动）；游标越界 → 关窗 |
| 响应 | `SubmitWindowResponse` | 二次校验 → 从窗口负载拿 `Tx` → `AppendModification(Req)`（交易侧 `Querying` 闸门再收一道，内部广播 `FTransactionModified`）→ `bAnyResponded=true` → 游标++ → 下一位 |
| 放弃 | `DeclineWindowResponse` | 同一套二次校验 → **不落任何账** → 游标++ → 下一位。**UI 倒计时到点也走本入口**（超时 = 直接请求关闭，§3.5） |
| 关窗 | `CloseTimingWindow` | **`ExitResponseLock()` 撤锁** + 广播 `FResponseLockChanged` → **先复位再广播 `FWindowClosed`**（回调里可立刻开新窗）→ 回调持有者（`Tx` 非空 → `OnWindowClosed`；空 → `Advance()` 续走） |

- **二次校验三条**（每条都拒绝 + Warning 日志）：① 窗口在场且锁内（锁外提交 = 无关输入）；② 提交者 = **当前正被询问者**（`InOrder` 下只有游标处的人有权；名单内但没轮到 = 拒绝）；③ 提交内容合法（在候选内 + 通过裁决——P3 最小集，目标/代价完整校验属 P5/P6）。
- **`bAnyResponded` 的语义 = "有人行使过响应权"**，不是"有修改被实际收下"（行为语义，非效果语义）：纯阶段窗（`Tx` 为空）的响应走 `PushPhaseResolvation` 不经 ModRequest，同样记为已回应。
- **纯阶段时机的回写路径**：技能对阶段的修正（Skip/Extra/Jump）由技能体自己写 `PushPhaseResolvation` → `PhaseMsgQueue`，关窗回调 `Advance()` 时由 `ResolveNextPhase` 消费——与交易的 `AppendModification` 通道并行不悖，两路在 `CloseTimingWindow` 的路由处分流。

### 3.5 关闭裁决与安全

- **关闭时机统一只通过 UI 决定**：引擎侧不持有任何定时器（不用 Timer/`WaitDelay`）；`FResponseWindow.Timeout` 只是随候选下发给 UI 的**时间预算**。
- UI 倒计时结束 → 客户端**直接请求关闭**：走与"放弃"同一 RPC 入口，服务端按当前响应者放弃收敛；全员弃 → 空结果关窗——绝不让回合卡死在窗上。
- 无人响应的窗口（绝大多数移动）成本 = 查索引空表 → 立即关窗，无延迟路径（这条直通与 UI 无关）。
- **现状**：`Timeout` 取 `UArkWarBattleSettings::DefaultWindowTimeout`（默认 10s），只随窗口数据下发；引擎侧确无定时器。
- 所有开窗/收响应仅服务器（`IsRunningOnServer` 门控贯穿）。
- 已知边界：UI 是唯一关闭裁决者——掉线/UI 未接入时窗口悬停、服务端无兜底（刻意保留，避免引擎内双裁决；P7 接 UI 时随断线处理一并复核）。

### 3.8 开窗通知链路与 `AppendModification`（`12` §4）

本阶段必须落地的"通知"四步：

1. `OpenTimingWindow` 内：查索引 → 合法预检 → 填 `Responders` → **广播 `FWindowOpened`**；
2. 询问：`State.Responding` 上锁 + 下发候选（§3.3）；
3. 响应者从窗口负载（= 交易引用）拿 `Tx` → `Tx->AppendModification(Req)`（交易侧唯一收口，`04` §4.1）→ **广播 `FTransactionModified`**；
4. `Close`：结果回写 → **广播 `FWindowClosed`** → 回调（阶段机 `Advance` / 交易 `OnWindowClosed`）。

> **现状**：四步链路已落地——① 填名单（`CollectResponders` 查索引 + 预检 + 排序） + `FWindowOpened`（`OpenTimingWindow`）② 上锁 + `AskNextResponder` 逐个询问 ③ `SubmitWindowResponse → Tx->AppendModification → FTransactionModified` ④ `CloseTimingWindow`（`FWindowClosed` + 回调）。P3 范围内的空转已清零；名单恒空只因尚无技能子类写入索引（子类订退内容不属本阶段，§3.3.1/§3.3.5）。

### 3.9 交易嵌套入口（`04` §3.2，字段与入口已落、续行点待裁）

- 字段：`NestedStack`（`TArray<FNestedTransactionFrame>`，定义见 `04` 附录 / `12` 附录 D）落 `UBattleGameFlowSubsystem`；
  **无 `MaxNestedDepth` 成员**（2026-09-16 裁：深度上限降为设计约定，不落运行期成员与校验，`04` §3.2 不变量 2）；
- 入口：`PushNestedTransaction` / `PopNestedTransaction` + **拒绝分支**（防环 / 非活动上下文 / 空子 / 非服务器）；
- **锚点（2026-09-16 定稿，硬约束）**：`ActiveTransaction` 已强化为 `UPROPERTY() TObjectPtr`（强持有 + 反射可见）；
  栈帧 `Parent`/`Child` 必须同为 `TStrongObjectPtr`——换手（`ActiveTransaction = Child`）后父的强引用只剩帧，
  弱引用会让父在子交易悬停期被 GC，出栈即悬空（`04` §3.2 不变量 1）；
- **收尾守卫**：`OnTransactionFinished` 落地嵌套分支——栈顶 `Child == Tx` → 只换手（弹栈 + `ActiveTransaction` 归父），

- **父的续行点**：`OnWindowClosed`/`Execute` 都是普通函数、无法在栈上等待；子交易若开窗（P5 濒死必开）
  就必须走"父的续行显式化"（`ResumeFromNested()`，由 `PopNestedTransaction` 调起，父的原调用栈在 Push 后返回）
  ——`04` §3.2 决策点，**与入队方式一并定稿**；
- **本阶段不做真实使用者**（P5 濒死首次使用）：只保证入口存在、拒绝路径可测（非活动上下文、或自嵌套 `Child == ActiveTransaction` 各构造一次调用 → 告警且不改变 `ActiveTransaction`）；
- 决策点（本阶段定稿后回填 `04` §3.2）：子交易入队方式 —— `Start(bool bNested)` vs `EnqueueNested()`。
- **现状（2026-09-16 更新）**：字段与入口**已落地**——`NestedStack` + `PushNestedTransaction`（门控 / 拒绝分支 → 建帧 / 换手 / `Child->Drive()`）+ `PopNestedTransaction`（栈顶自校 / 弹栈 / 换手回父）+ `OnTransactionFinished` 栈顶判定分支（`04` §3.2、`12` §9 同步回填）。**父的续行点仍未裁**（`Pop` 内留 TODO）。
