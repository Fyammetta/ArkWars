### 3.2 窗口生命周期实现（`03` §4 → `10` §2/§4）

类型已随 `EventTypes.h` 预置（与 `12` 附录 B 一致；**命名以代码为准**）：

```cpp
// 窗口内一条可响应项（EventTypes.h）
struct FResponseEntry
{
    TStrongObjectPtr<UBattleTransaction> Tx;   // 关联交易（窗口负载；纯阶段时机可空）
    int32 Priority;                            // 本窗内响应次序 = 开窗时算出的相对座次序快照（10 §2；同座多技能取注册稳定序；非技能数据）
    TWeakObjectPtr<APlayerState> Owner;        // 响应者所属玩家
    FGameplayTag Key;                          // 响应者技能标识（时机索引的键值来源）
};

// 窗口基座（EventTypes.h；EWindowPolicy 不在此形状内，走 OpenTimingWindow 参数，见 10 §2）
struct FResponseWindow
{
    FGameplayTag Timing;                      // 本次窗口对应的查询时机（Event.Timing.*，03 §3.1）
    TStrongObjectPtr<UBattleTransaction> Tx;  // 关联交易（强持有防窗口悬停期被 GC；可空：纯阶段时机）
    TArray<FResponseEntry> Responders;        // 合法响应者名单（开窗时由时机索引 + 合法预检填出）
    float Timeout;                            // 下发给 UI 的时间预算（秒）：关闭时机统一只通过 UI 决定，倒计时到点 UI 直接请求关闭（引擎侧无定时器，§3.5）
};
```

- **开窗者只有一个入口**（`OpenTimingWindow(TimingTag, Tx, Policy)`，放流程子系统或独立窗口管理器；`Tx` 即窗口负载成员、`Policy` 为 `10` §2 策略参数），阶段机与交易驱动共用；杜绝第二套窗口实现。
- 关窗 = 汇总结果回写（修改交易字段 / 写入 `PendingModifiers`）→ 回调（阶段机 `Advance` 续走 或 交易 `OnWindowClosed`）。任何路径不悬挂。

### 3.3 响应的发现与询问（`03` §5、`10` §2/§5）

> 本节回答两个问题：**窗口怎么知道该问谁**（发现，§3.3.1–§3.3.3）与**知道之后怎么问**（询问，§3.3.4）。
> 先立大前提（`12` §2 三面宪法 / `ArkWarDelegates.h` 文件头）：**A 面事实自己订，B 面查询等点名**——
> 事实通知（`Notify.*`）走委托自订阅，技能组件各自管理，去中心化；查询窗口（`Timing.*`）**不许自订阅**，
> 必须经中央索引被"点名"。本节只讲 B 面。

#### 3.3.1 发现：时机索引——为什么技能组件不能自己订阅时机

窗口的询问是一门有程序的生意，四件事缺一不可，而委托订阅表一件都给不了：

| 窗口需要 | 自订阅委托给不了的原因 |
|---|---|
| **排序名单**（谁先被问是玩法本身） | 多播委托调用序 = 注册序；注册序取决于组件谁先 `BeginPlay`——把玩法次序押在初始化时序上不可接受 |
| **问前预检**（不合格的不进名单） | 委托是"广播到即被调"，没有"先筛再问"这一拍 |
| **逐人询问**（`InOrder` 一次只问一人、悬停等 RPC） | 广播是一口气全放，节奏无法攥在窗口手里 |
| **容忍退场**（技能组件中途销毁） | 忘退订 = 悬垂回调；索引持弱引用、开窗时逐个验活，死掉的天然出局 |

所以 `USkillManagerSubsystem` 建**时机 → 监听技能**索引（形状施工时定，语义如下）：

```cpp
// 键 = Event.Timing.* 标签；值 = 在听这个时机的技能条目（形状已落：USkillManagerSubsystem::SkillTimings）
TMap<FGameplayTag, TArray<FSkillListenerEntry>> SkillTimings;
// FSkillListenerEntry（ArkWarSkillTypes.h）= { TWeakObjectPtr<USkillComponentBase> Skill,
//   TWeakObjectPtr<APlayerState> Owner } + IsValid()（两者俱活）/ operator==（只比 Skill）
// 登记册只存"关系"，刻意不存三样原料，一律开庭现取：
//   Key      —— 权威在组件（USkillComponentBase 持有 FSkillInfo，取用走 GetSkillTag()；
//               CreateSkill 已把技能 Tag 挂上 ComponentTags 供 FindComponentByTag 反查）
//   Priority —— 非技能数据：开窗现算的相对座次序（InOrder）；All/FirstOnly 同时发生无序（§3.3.2）
//   座次     —— 局内活状态，实时读 PhaseComponent（§3.3.2）
// 组件已死的条目整个作废（验活出局；RegisterSkillTiming 的 Entry.IsValid() 即第一道关），
// 不存在"需要 Key 而组件不在"的场合——故 Key 无须副本
```

**订阅权归子类，基类不做限制**：`USkillComponentBase` 只做两件事——宿主（把 `FSkillInfo::SkillClass` 实例化到 PlayerState，见 `09` §6）与便利（`CreateSkill` 工厂 / `GetSkillTag()` / `OnCanActivate()` 钩子）；**它不规定**听哪些时机、何时订阅、要不要统一登记口，也**不代劳**登记。订与退一律由**技能组件子类**自行实现（子类经 `UBattleFunctionLibrary::GetSkillManager(Owner)` 拿 `USkillManagerSubsystem`，直调 `RegisterSkillTiming` / `UnregisterSkillTiming`）：

- **订阅时机自由**：构造 / `BeginPlay` / 首次使用 / 按需动态增删，基类不强制某一处，也不检查有没有订阅；
- **订阅集合自由**：一件技能组件听 0~N 个时机、中途改集合，都合法；集合是子类的实现细节，**不上升为基类/声明数据的统一字段**（`FSkillInfo` 不新增"监听时机表"，引擎不替子类读它）；
- **退订责任在子类**：`EndPlay` / `DestroyComponent` / 形态切换时自行 `UnregisterSkillTiming`——即使忘退，索引侧也只持弱引用，开窗时验活出局（§3.3.3），不会悬垂。

**宿主侧顺序**（`CreateSkill` 已定）：打 `ComponentTags`（技能 Tag）→ 延迟注册 → `RegisterComponent` 触发 `BeginPlay`——保证子类在 `BeginPlay` 里就能拿到 `GetSkillTag()` 与索引去订阅。
订阅完，"何时被问、第几个被问、有没有资格被问"全由窗口按策略裁决——组件只管"听了什么"，不管"何时被调用"。

> **现状（P3 §3.3.1）**：索引本体已落——`SkillTimings` + `RegisterSkillTiming`（门控 + 验活 + 查重）/ `UnregisterSkillTiming`（门控 + 空指针校验 + 销账查无此人告警）/ `GetSkillListeners`（门控 + 按值返回快照，遍历期源表可增删）。宿主侧 `CreateSkill` 工厂（查重 → `GetCurrentSkillByTag` 取声明 → `bDeferred` 注册 → 挂 `ComponentTags`）、`GetSkillTag()`、`OnCanActivate()` 钩子已落。**未落**：订阅动作本身——按本节口径它归技能**子类**自行实现，基类不代办（`USkillComponentBase::BeginPlay` 保持空实现），故索引目前尚无写入方；`CollectResponders` 接索引仍返回空表（§3.3.5）。

**查表成本**：索引空表 = 直通（§7），绝大多数移动窗走这条零延迟路径；这也是"无监听直通优先于整点全开"的底气。

#### 3.3.2 排序：次序 = 座次（开窗实时读取）

**不设技能级 `ResponsePriority`**（`09` 原字段已废）：次序不是技能的属性，是**局面的属性**——
同一门技能，坐的位置不同、当庄的人不同，被问的先后就不同。`CollectResponders` 开庭填名单时按策略口径排序（`10` §2）：

- **`InOrder`（逐人询问）**：名单序 = **座次**——从**当前回合玩家**起顺/逆时针旋转（`ISeatLayout`，方向规则表可配）。座次不是数组裸下标，是**以行动者为起点的相对序**：同一份名单，换人当庄，询问序整体轮转。`FResponseEntry.Priority` 字段 = 这个相对序数的快照（供 UI 显示/日志），**不是技能数据**；
- **同座多技能**：同一玩家的多门技能之间无玩法先后，取**注册稳定序**兜底——注册序**不承载玩法语义**，唯一职责是确定性（同局面收敛可复现，回放对账，`11` §7）；
- **`All` / `FirstOnly`**：**无序**——现实层面同时发生，各自独立决定 / 首响生效，名单只是有权者集合，`Priority` 不填或恒 0。

**座次的唯一权威 = `UGamePhaseManagerComponent` 的 `PlayersInOrder` + `ActivePlayerIndex`（旋转起点）**，
且必须**开窗那一刻实时读取、现场计算**——索引与任何登记数据**不存座次快照**：

- 理由：存在调换座次类效果（换座/易位），座次是局内活状态。若登记快照，换座技能就要挨家挨户改副本，
  漏改一处 = 询问序静默错一轮，且名单看着齐整、极难验尸；
- 实时读取让换座效果的实现成本归零：它只改 `PhaseComponent` 那一份权威，下一扇窗自动用新座次，全系统没有第二份座次需要对账；
- 实现材料是现成的：`UBattleGameFlowSubsystem` 自带 `GetPhaseManager()` / `GetPlayerIndex(Player)`；两字段均为复制字段，客户端 UI 显示"等待谁响应"与服务端名单序天然同源。

**快照时刻 = 开窗填出 `Responders` 之时**（窗内冻结、窗外实时）：名单与次序自此冻结，本窗按它问到底；
悬停期发生换座**不影响进行中的窗**（中途改序 = 开庭换法官），新座次自下一窗生效。
悬停期玩家**离场**不适用本条——那是失效传播（`10` §3，P7）的地界。

#### 3.3.3 预检：进名单前的资格审查

候选只表示"这个时机有技能在听"，入名单前逐个过闸（`10` §4）：

- **来源在场**：所属玩家在场且未出局（弱引用验活在此一并做）；
- **技能可用**：组件存活、未被封印（封印类状态效果属 P7，P3 只验存活）；
- **账本余量**：频率/代价可付（`07`）——**P6 前常量放行**，代码留占位注释。

预检不过 = 不进名单，**有日志**（自动方也过同一道预检，`10` §4）。

#### 3.3.4 询问：InOrder 最小流程（与现行实现的对照表）

| 步骤 | 落点函数 | 做什么 |
|---|---|---|
| 开窗 | `OpenTimingWindow` | 门控 → 单层保护 → `CollectResponders`（§3.3.1–3）→ 广播 `FWindowOpened` → 空名单直通关窗 / 上锁 `State.Responding`（`bRespondingLock`）→ 进询问 |
| 逐人问 | `AskNextResponder` | 游标有效 → 给 `Responders[游标].Owner` 的客户端下发"你有响应权 + 候选"（附 `Timeout` 时间预算）→ **返回**（引擎不等待，推进纯事件驱动）；游标越界 → 关窗 |
| 响应 | `SubmitWindowResponse` | 二次校验 → 从窗口负载拿 `Tx` → `AppendModification(Req)`（交易侧 `Querying` 闸门再收一道，内部广播 `FTransactionModified`）→ `bAnyResponded=true` → 游标++ → 下一位 |
| 放弃 | `DeclineWindowResponse` | 同一套二次校验 → **不落任何账** → 游标++ → 下一位。**UI 倒计时到点也走本入口**（超时 = 直接请求关闭，§3.5） |
| 关窗 | `CloseTimingWindow` | 撤锁 → **先复位再广播**（回调里可立刻开新窗）→ `FWindowClosed` → 回调持有者（`Tx` 非空 → `OnWindowClosed`；空 → `Advance()` 续走） |

- **二次校验三条**（每条都拒绝 + Warning 日志）：① 窗口在场且锁内（锁外提交 = 无关输入）；② 提交者 = **当前正被询问者**（`InOrder` 下只有游标处的人有权；名单内但没轮到 = 拒绝）；③ 提交内容合法（在候选内 + 通过裁决——P3 最小集，目标/代价完整校验属 P5/P6）。
- **`bAnyResponded` 的语义 = "有人行使过响应权"**，不是"有修改被实际收下"（行为语义，非效果语义）：纯阶段窗（`Tx` 为空）的响应走 `PushPhaseResolvation` 不经 ModRequest，同样记为已回应。
- **纯阶段时机的回写路径**：技能对阶段的修正（Skip/Extra/Jump）由技能体自己写 `PushPhaseResolvation` → `PhaseMsgQueue`，关窗回调 `Advance()` 时由 `ResolveNextPhase` 消费——与交易的 `AppendModification` 通道并行不悖，两路在 `CloseTimingWindow` 的路由处分流。

### 3.4 两个接线点（改动极小、是 P3 的全部引擎 diff）

```
① 02 §3.2：Advance 遇 _Pre/_Post → OpenTimingWindow(该点时机) → 等关窗回调 → Advance()
   （关窗回调里把响应结果（Skip/Extra/Jump）写 PendingModifiers → 再 Advance，修正裁决照旧）
② 04 §3：DriveTransaction 内 Active->Drive();     ← 调用方不变
                    只需改基类 Drive() 体：Execute(); → QueryTimings();  // 开窗即返、不清 ActiveTransaction（忙锁继续）
   QueryTimings()（P2 置 Querying 占位 → P3 填）：逐个开 Tx = this 的查询时机（如 Event.Timing.Card.PreMove）
   OnWindowClosed()（P2 空 → P3 填）：汇总响应结果 → 被防/无效 → Finish(false)（族钩子
   BroadcastFinish(false) 广播防止通知，不 Execute）；否则 Execute()（族自收尾 Finish(true/false)）
```

- 交易自身零改动：P2 就位的 `Finish(bool)` 唯一收尾（落 `Finished` → `BroadcastFinish(bool)` → `OnTransactionFinished` 踢链）直接复用；被防/无效不再是第二入口，只是 `Finish(false)` 的语义路径。
- 阶段机侧：技能响应（如"判定前跳过"）需在窗口关闭后**先应用修正再推进**，顺序约定写在 `03` §4 与 `02` §3。
- **现状**：② 已落地（`Drive()` 体已是 `QueryTimings()`；`QueryTimings`/`OnWindowClosed` 已填实，含多时机逐个开窗）；① 未落地（`Advance()` 仍直通 `_Pre/_Post`，无 `OpenTimingWindow` 调用）——但关窗回调的纯阶段分支（`Tx == nullptr → Advance()`）已在 `CloseTimingWindow` 就位，只差接缝。

### 3.5 关闭裁决与安全

- **关闭时机统一只通过 UI 决定**：引擎侧不持有任何定时器（不用 Timer/`WaitDelay`）；`FResponseWindow.Timeout` 只是随候选下发给 UI 的**时间预算**。
- UI 倒计时结束 → 客户端**直接请求关闭**：走与"放弃"同一 RPC 入口，服务端按当前响应者放弃收敛；全员弃 → 空结果关窗——绝不让回合卡死在窗上。
- 无人响应的窗口（绝大多数移动）成本 = 查索引空表 → 立即关窗，无延迟路径（这条直通与 UI 无关）。
- **现状**：`Timeout` 取 `UArkWarBattleSettings::DefaultWindowTimeout`（默认 10s），只随窗口数据下发；引擎侧确无定时器。
- 所有开窗/收响应仅服务器（`IsRunningOnServer` 门控贯穿）。
- 已知边界：UI 是唯一关闭裁决者——掉线/UI 未接入时窗口悬停、服务端无兜底（刻意保留，避免引擎内双裁决；P7 接 UI 时随断线处理一并复核）。

### 3.8 开窗通知链路与 `AppendModification`（`12` §4）

本阶段必须落地的"通知"四步：

1. `OpenTimingWindow` 内：查索引 → 合法预检 → 填 `Responders` → **广播 `FWindowOpened`**；
2. 询问：`State.Responding` 上锁 + 下发候选（§3.3）；
3. 响应者从窗口负载（= 交易引用）拿 `Tx` → `Tx->AppendModification(Req)`（交易侧唯一收口，`04` §4.1）→ **广播 `FTransactionModified`**；
4. `Close`：结果回写 → **广播 `FWindowClosed`** → 回调（阶段机 `Advance` / 交易 `OnWindowClosed`）。

> **现状**：四步链路已落地——① 填名单 + `FWindowOpened`（`OpenTimingWindow`）② 上锁 + `AskNextResponder` 逐个询问 ③ `SubmitWindowResponse → Tx->AppendModification → FTransactionModified` ④ `CloseTimingWindow`（`FWindowClosed` + 回调）。唯一空转处是 `CollectResponders` 尚未接时机索引（返回空表 → 走"无监听直通"，§3.3）。
