## 3. 交易基类 `UBattleTransaction`

按设计 §5.1 落地四态生命周期，但 P2 不接时机窗口，先让「创建 → 执行 → 完成」主干跑通。**现状**：`UBattleTransaction` 骨架已落地（`Battle/Transaction/`）但方法全空，且与本节蓝图存在命名差异（代码有 `End()` 无 `Cancel()`、`Instigator/Target` 是 `TWeakObjectPtr<AActor>`、`Execute` 用 `PURE_VIRTUAL` 宏）——施工时以本节代码块为目标形态，先按 §11-2 对齐差异再填实现：

```cpp
UCLASS(Abstract)
class ARKWARS_API UBattleTransaction : public UObject
{
	GENERATED_BODY()
public:
	enum class EState : uint8 { Created, Querying, Executed, Finished };

	TObjectPtr<APlayerState> Instigator;   // 发起者（可空：桌面级移动无归属）
	TObjectPtr<APlayerState> Target;       // 目标玩家（可空）

	// ── P2 实现：同步主干 ──────────────────────────────────
	void Begin();                          // 校验字段 → Created → EnqueueTransaction
	virtual void Execute() PURE;           // 纯虚：真正的落子，子类实现；以 Finish()/Cancel() 自收尾
	void Finish();                         // 置 Finished → 最小通知 → 回调管理器 OnTransactionFinished
	void Cancel();                         // 被防止/无效化 → 置 Finished（不 Execute）→ 回调管理器 OnTransactionFinished
	EState GetState() const { return State; }

	// ── P3 预留：时机窗口骨架（本阶段声明 + 空实现占位，驱动流程不调用）──
	void QueryTimings();                   // P3：逐个开查询时机窗口（异步，可被修改/取消）；P2 空转直通
	void NotifyTimings();                  // P3：事实通知细分（AreaEnter/AreaLeave）；P2 的最小通知留在 Finish 内
	void OnWindowClosed();                 // P3：窗口关闭后由流程回调驱动生命周期前进；参数 FResponseWindow 属 P3 类型，届时补

protected:
	EState State = EState::Created;
};
```

> 命名说明：蓝图里没有独立的 `End()`——生命周期的正常终点是 `Finish()`，被防止/取消走 `Cancel()`，两者都落入终态 `Finished`，区别只在「是否执行过 `Execute`」。注意**实际代码目前有一个空的 `End()` 且没有 `Cancel`**（差异见 §11-2），施工时按蓝图统一为 `Finish`/`Cancel`。

### 3.1 各方法职责

| 方法 | 谁调用 | 做什么 |
|---|---|---|
| `Begin()` | 创建方（阶段体 / 技能 / 调试入口） | ① 校验必填字段（`From`/`To` 不能是无效标签）；② 置 `State = Created`；③ 把自己登记进流程的交易队列 `EnqueueTransaction(this)` |
| `Execute()` | 管理器（出队时） | 纯虚，子类实现真正的落子（移动 / 伤害 / 濒死）。**结束时必须自行调用 `Finish()`（成功）或 `Cancel()`（失败 / 被防止）** |
| `Finish()` | `Execute()` 内部（成功路径） | ① 置 `State = Finished`；② 广播「已完成」类事实通知（P2 最小：`Event.Notify.Card.Moved`，P3 再细分 AreaEnter/AreaLeave）；③ 回调管理器 `OnTransactionFinished(this)` 继续出队 |
| `Cancel()` | `Execute()` 内部（P3 亦由窗口响应触发） | ① 置 `State = Finished`（不执行落子）；② 广播「被防止」类事实通知（P2 占位，P3 接 `Event.Notify.Damage.Prevented` 等）；③ 回调管理器 `OnTransactionFinished(this)` 继续出队 |
| `QueryTimings()` | 管理器（P3 驱动时） | **P3 实现**：逐个开查询时机窗口，窗口可改/取消本次结算；**P2 空实现占位**，同步驱动不调用 |
| `NotifyTimings()` | `Finish()`/`Cancel()`（P3） | **P3 实现**：细分 `AreaEnter`/`AreaLeave` 事实通知；**P2 空实现占位**（P2 通知在 `Finish` 内直发） |
| `OnWindowClosed()` | 响应窗口（P3） | **P3 实现**：汇总窗口结果 → 走 `Execute`/`Finish` 或 `Cancel`；**P2 空实现占位**（无人调用） |

生命周期两条路径（P2 同步直通；P3 在 `Execute` 前插入 `QueryTimings → 窗口 → OnWindowClosed` 一段，见 §3.4）：

```
正常：   Begin → Execute → Finish → OnTransactionFinished →（驱动下一条）
被防止： Begin → Cancel   → OnTransactionFinished →（驱动下一条）
```

要点：

- **`Execute` 是「自收尾」的**：它要么 `Finish()` 要么 `Cancel()`，两者都会回调管理器 `OnTransactionFinished` 踢下一条。P3 引入异步窗口后收尾动作不变——窗口关闭最终也收敛到 `Finish`/`Cancel`，交易对外接口不动。
- 交易是 `UObject`，由流程侧 `NewObject<UCardMoveTransaction>()` 创建、出队即用；不挂到 Actor，不参与复制。
- `QueryTimings()`/`NotifyTimings()`/`OnWindowClosed()` 本阶段**声明并空实现**，只占接口不占行为，见 §3.4 占位清单。

### 3.2 管理器：`UBattleGameFlowSubsystem` 需要新增什么

P1 只有回合 FSM，P2 给同一子系统补上「交易队列」的承载与驱动。**驱动形态直接从 P2 就采用 P3 的「单条驱动 + 收尾踢」**——同步下行为等价于 while 清空，但结构已是回调驱动，P3 只改一行。**现状**：字段 `PendingTransactions`（`TArray<UBattleTransaction*>`）/`ActiveTransactionIndex`（`int32`）已声明；`EnqueueTransaction`/`ProcessTransaction`（单数，即下方拆分的旧名）仅剩服务器门控桩，未入队未驱动。施工时按下方案例落地并把 `ActiveTransactionIndex` 用法对齐下方 `ActiveTransaction` 指针形态：

```cpp
// UBattleGameFlowSubsystem —— P2 新增
UPROPERTY()
TArray<TObjectPtr<UBattleTransaction>> PendingTransactions;   // 交易队列（FIFO）

TObjectPtr<UBattleTransaction> ActiveTransaction;             // 忙锁：非空 = 正在执行 /（P3）窗口悬停，禁止重入

void EnqueueTransaction(UBattleTransaction* Tx);              // 入队；不忙则立即 DriveTransaction
void DriveTransaction();                                      // 驱动单条：出队 → Execute（P3 唯一改动点：Execute → QueryTimings）
void OnTransactionFinished(UBattleTransaction* Tx);           // 收尾回调：清 Active → 驱动下一条
```

管理器职责：

1. **入队**：`EnqueueTransaction(Tx)` —— `Tx->Begin()` 时把自己推入 `PendingTransactions`，随即调 `DriveTransaction()`；忙（`ActiveTransaction` 非空）则只入队，等当前交易收尾回调再处理。
2. **单条驱动**：`DriveTransaction()` —— `ActiveTransaction` 非空直接返回（防重入，这是窗口悬停期唯一的锁）；出队队首置为 `ActiveTransaction` 并 `Execute()`。`Execute` 内以 `Finish`/`Cancel` 自收尾，收尾里回调 `OnTransactionFinished`。
3. **收尾踢**：`OnTransactionFinished(Tx)` —— 确认当前活动交易是 `Tx` 后清空 `ActiveTransaction`，再 `DriveTransaction()` 踢下一条，直到队列空。保证「一条结算完才轮到下一条」。
4. **服务器门控**：所有方法仅在 `IsRunningOnServer()` 下有效；客户端不跑任何交易。
5. **嵌套预留（P3）**：`ActiveTransaction` 非空即忙锁，天然挡住窗口悬停期的重复驱动；濒死等「打断当前流程」的嵌套用显式栈管理（设计 §5.3），P2 只留字段、不实现。

```cpp
void UBattleGameFlowSubsystem::EnqueueTransaction(UBattleTransaction* Tx)
{
	if (!Tx || !IsRunningOnServer()) return;
	PendingTransactions.Add(Tx);
	DriveTransaction();          // 忙（Active 非空）时内部直接返回；当前交易收尾回调后自会踢到本条
}

void UBattleGameFlowSubsystem::DriveTransaction()
{
	if (!IsRunningOnServer() || ActiveTransaction) return;   // 忙锁：P3 窗口悬停期同样靠它防重入
	if (PendingTransactions.IsEmpty()) return;

	ActiveTransaction = PendingTransactions[0];
	PendingTransactions.RemoveAt(0);
	ActiveTransaction->Execute();
	// P3 唯一改动点：上面这行换成 ActiveTransaction->QueryTimings();
	// 开窗即返、不清 ActiveTransaction；窗口关闭 → OnWindowClosed → Finish/Cancel → OnTransactionFinished
	// （P2 同步：Execute 内跑完，收尾回调即触发，连锁清空队列 = 原 while 版本的效果）
}

void UBattleGameFlowSubsystem::OnTransactionFinished(UBattleTransaction* Tx)
{
	if (ActiveTransaction != Tx) return;
	ActiveTransaction = nullptr;
	DriveTransaction();          // 踢下一条
}
```

> 串行的自然效果：`Execute()` 内部若又 `Enqueue` 新交易（响应 / 嵌套产生的新结算），因 `ActiveTransaction` 非空仅入队不驱动；当前交易 `Finish`/`Cancel` 收尾回调 `OnTransactionFinished` 后，新交易才被踢到。这就是设计 §5.3「不递归、排队执行」的实现，且**同步与 P3 同构**：P3 只需把 `DriveTransaction` 内的 `Execute()` 换成 `QueryTimings()`（开窗即返、不清 `ActiveTransaction`），收尾链一行不改。

## 4. `UCardMoveTransaction`

按设计 §7 从第一天交易化：

```cpp
UCLASS()
class ARKWARS_API UCardMoveTransaction : public UBattleTransaction
{
	GENERATED_BODY()
public:
	GameMessage::FMoveMessage Move;                 // 解析后的意图（From/To/Num/Predicate/Order）
	TArray<FGameplayTagContainer> Resolved;         // 实际选中待移动的牌
	virtual void Execute() override;
};
```

`Execute()`（服务器侧）主流程：

```cpp
void UCardMoveTransaction::Execute()
{
	// 1. 区域 → 容器（见 §6）
	ICardContainerInterface* From = ResolveContainer(Instigator, Move._From);
	ICardContainerInterface* To   = ResolveContainer(Target,    Move._To);
	if (!From || !To) { Cancel(); return; }

	// 2. 取源区候选牌 → 用 FMoveMessage 过滤/截取
	//    只读出口已实现为接口级 GetCardsByKey(Key)/GetAreaKeys()（见 §5.2 尾注）
	TArray<FGameplayTagContainer> Candidates = From->GetCardsByKey(Move._From);
	Resolved = Move(Candidates);                // 命中 Predicate + Count + Order

	// 3. 落子：源出、目标入（Msg 传保留原文的 _Meta）
	From->MoveOut(To, Resolved, Move._Meta);
	To->MoveIn(From, MoveTemp(Resolved), Move._Meta);

	Finish();
}
```

要点：

- `Move(Candidates)` 直接复用 `FMoveMessage::operator()(const TArray<FGameplayTagContainer>&)`，按 `_Count` 截取前 N 张（`_Order` 影响取牌顺序，P2 先支持 Top，Random/Botton 留测试兜底）。
- `_From == _To`（如整理手牌顺序）直接 `SetCardOrder`，不走 MoveOut/MoveIn。
- 客户端不跑上述任何逻辑，只等复制后的区域属性与事实通知。

## 5. 容器 `MoveIn/MoveOut` 实现

两侧各只关心**自己这一端**的区域：

- `MoveOut(To, Cards, Msg)`：按 `FMoveMessage(Msg)._From` 决定从哪个自身区域移除。
- `MoveIn(From, Cards, Msg)`：按 `FMoveMessage(Msg)._To` 决定加入哪个自身区域。

### 5.1 玩家侧 `UCardManagementBusComponent`

```cpp
void UCardManagementBusComponent::MoveIn(ICardContainerInterface* From, TArray<FGameplayTagContainer>&& Cards, const FString& Msg)
{
	if (!HasAuthority()) return;
	const GameMessage::FMoveMessage Move(Msg);
	if (Move._To == CardTags::Hand)
		HandCards.Append(Cards);
	else if (Move._To == CardTags::Equipment)
		/* 按装备类别键找/建 FCardAreaSlot 塞入 */
		;
	else if (Move._To == CardTags::Judgement)
		/* 判定区每张牌一个槽 */
		;
}

void UCardManagementBusComponent::MoveOut(ICardContainerInterface* To, const TArray<FGameplayTagContainer>& Cards, const FString& Msg)
{
	if (!HasAuthority()) return;
	const GameMessage::FMoveMessage Move(Msg);
	if (Move._From == CardTags::Hand)
		for (const auto& C : Cards) HandCards.Remove(C);
	else if (Move._From == CardTags::Equipment) /* 从对应槽 Remove */
		;
	else if (Move._From == CardTags::Judgement) /* 从对应槽 Remove */
		;
}
```

- `EquipmentArea`/`JudgementArea` 是 `TArray<FCardAreaSlot>`，`FCardAreaSlot` 提供 `Add`/`Remove`，容量由槽的 `Capacity` 约束。
- 复制：三处区域字段均已 `DOREPLIFETIME`，改完即同步；`FCardAreaSlot` 作为 `TArray` 元素随容器一起复制即可。

### 5.2 桌面侧 `ACardTableManager`

```cpp
void ACardTableManager::MoveIn(ICardContainerInterface* From, TArray<FGameplayTagContainer>&& Cards, const FString& Msg)
{
	if (!HasAuthority()) return;
	const GameMessage::FMoveMessage Move(Msg);
	if (Move._To == CardTags::Pile)          PileArea.Append(Cards);
	else if (Move._To == CardTags::Discard)  DiscardArea.Append(Cards);
	else if (Move._To == CardTags::Cache)    CachedArea.Append(Cards);
	else if (Move._To == CardTags::Used)     PlayedArea.Append(Cards);
}
```

- `PileArea`/`DiscardArea` 已各自绑定独立 OnRep（见 §2-4 ✅），各区域复制刷新独立，客户端可区分来源。
- `MoveOut` 对称地从对应区域 `Remove`。
- ✅ 只读出口**已实现**为接口级 `GetCardsByKey(Key)`/`GetAreaKeys()`：玩家侧按 Key 返回 Hand/Equipment/Judgement 并可委托同 Owner 的其他容器组件；桌面侧各区域直取。§4 候选枚举直接用 `From->GetCardsByKey(Move._From)`，原「补 `GetCards`」计划作废。

## 6. 区域解析入口

唯一入口，把 `FGameplayTag` 区域映射为容器对象（建议放 `UBattleGameFlowSubsystem` 或 `BattleFunctionLibrary`）：

```cpp
ICardContainerInterface* ResolveContainer(APlayerState* Owner, const FGameplayTag& Area)
{
	// 玩家区域 → PlayerState 上的 CardManagementBusComponent
	if (Area == CardTags::Hand || Area == CardTags::Equipment || Area == CardTags::Judgement)
		return Owner ? Owner->FindComponentByClass<UCardManagementBusComponent>() : nullptr;
	// 桌面区域（Pile/Discard/Cache/Used 等）→ 世界单例
	return ACardTableManager::Get(World);
}
```

- 桌面区域（`Card.Area.Pile/Discard/Cache/Used`）→ `ACardTableManager::Get(World)`（世界单例，服务器侧可 Spawn）。
- 玩家区域（`Card.Area.Hand/Equipment/Judgement`）→ 玩家 `PlayerState` 上的 `UCardManagementBusComponent`。
- `Owner`/`Target` 为空时的归属规则（如桌面到桌面、无主摸牌）在此统一约定，避免每个交易各自散落判断。

## 8. 验收方式

1. **单步移动**：服务器调测试入口发起一条 `UCardMoveTransaction`（`PushPhase` 风格的调试命令），日志打印 `[Move] From=X To=Y Num=N`，确认源区减、目标区加。
2. **全链路可见**：客户端确认 `HandCards`/`PileArea` 等复制到位，日志能读到移动前后数量。
3. **DSL 回归**：§7 用例表逐条跑通；重点回归 `AREA=` 边界与 §2-5 的 `_bDiscard` 判定（判真写法与 DISCARD 值解析须先修）。
4. **守恒对账**：任意移动后，全局卡牌总数不变（源减 + 目标加 = 0）。
5. 日志一律英文（`LogCard` 类别），区域名从 `CardTags::*` 取，勿硬编码字符串。
