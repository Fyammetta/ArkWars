# ArkWars 战斗流程与时机系统设计

> 本文档基于现有代码（`Battle/` 模块）的评审结论，给出后续战斗框架的设计方案。
> 核心命题：**回合流程是同步的状态机；技能干预点是异步的响应窗口；结算行为是生命周期完整的交易对象。**

---

## 1. 总体原则

| 原则 | 说明 |
|---|---|
| 服务器权威 | 一切规则裁决只在服务器发生。客户端不运行流程逻辑，只消费复制结果与演出。 |
| 事件二分 | **事实通知**（已发生、不可否决）保持同步多播；**时机查询**（未发生、可被干预）走异步响应窗口。两者绝不混用一条通道。 |
| 结算交易化 | 伤害、移动卡牌、濒死等结算行为不是函数调用，而是有生命周期的交易对象（Transaction）。"延迟结算"即交易悬停在查询阶段。 |
| 规则与表现分离 | 服务器规则层不等待动画。客户端的异步性由本地表现队列消化，不反向影响规则。 |
| GAS 的边界 | GAS 负责：技能体（Ability）、触发负载（GameplayEventData）、属性与最终数值修改（GE）。GAS 不负责时序裁决——时序归流程系统。 |

## 3. 阶段状态机（同步主干）

### 3.1 阶段枚举语义

沿用现有 `EGamePhase`，三档后缀的语义固定如下：

| 后缀 | 语义 | 执行方式 |
|---|---|---|
| `Xxx_Pre` | **查询时机点**："进入 X 阶段前"，技能可干预（跳过/追加/触发效果） | 异步响应窗口 |
| `Xxx` | **阶段本体**：遍历判定区、摸牌、弃牌等规则逻辑 | 同步执行 |
| `Xxx_Post` | **查询时机点**："X 阶段结束时"，触发类技能挂载点 | 异步响应窗口 |

完整顺序：
`GameStart → Begin → Preparation_Pre → Preparation → Preparation_Post → Judgment_Pre → Judgment → Judgment_Post → Draw_Pre → Draw → Draw_Post → Action_Pre → Action → Action_Post → Discard_Pre → Discard → Discard_Post → Finish →（下一位玩家的 Begin）`

### 3.2 推进流程（服务器）

```cpp
// UBattleGameFlowSubsystem::Advance —— 伪代码
void UBattleGameFlowSubsystem::Advance()
{
    // 1. 应用阶段修正队列（SKIP/EXTRA/JUMP，来自 CardMsgDef.h 已预留的三个Key）
    const EGamePhase Next = ResolvePhaseModifiers(CurrentPhase);

    // 2. 前置查询时机（异步）：开窗口等响应；期间阶段尚未真正切换
    OpenTimingWindow(Tag_Timing_Phase_Pre(Next), /*payload*/);
    // 窗口关闭回调 ↓
}

void UBattleGameFlowSubsystem::OnPreWindowClosed(...)
{
    // 3. 若未被 SKIP/JUMP 改写：切换阶段（复制），同步执行阶段本体逻辑
    PhaseManager->SetPhase(CurrentPhase);      // 事实：同步广播 + 复制
    ExecutePhaseBody(CurrentPhase);            // 判定区遍历/摸牌/弃牌……

    // 4. 后置查询时机（异步）
    OpenTimingWindow(Tag_Timing_Phase_Post(CurrentPhase), ...);
    // 窗口关闭后 → 再次 Advance()
}
```

要点：

- `SetPhase` 只在服务器调用（现有代码已做 `HasAuthority` 检查，保留）。
- **阶段本体是同步的**：摸牌、判定区结算这类不需要等待干预的逻辑，不引入任何异步等待。
- 回合轮转：`Finish` 关闭后，经 `SetNextPlayerActive()` 切换到下一位玩家，回到 `Begin`。

### 3.3 阶段修正队列

`CardMsgDef.h` 已预留 `SKIP / EXTRA / JUMP` 三个 Key。设计为队列而非单值：

```cpp
// 一次窗口内可能叠加多个修正（如两个技能分别跳过摸牌、追加出牌）
TArray<FPhaseModifier> PendingModifiers;  // 按 FIFO 结算：JUMP 优先于 SKIP/EXTRA
```

## 4. 时机点系统（事件二分）

### 4.1 两条通道

```
事实通知通道（保留现有形态：同步多播委托 / RepNotify）
    FGamePhaseChangeDelegate / FActivePlayerChangeDelegate / ...
    含义：事情已发生。订阅者只读、只反应，不可否决。

查询时机通道（新增：异步响应窗口）
    Event.Timing.* 标签 + 交易负载
    含义：事情将发生。响应者可修改、阻止、替代。
```

### 4.2 时机标签命名规范

```
Event.Timing.Phase.{PhaseName}.Pre      进入阶段前
Event.Timing.Phase.{PhaseName}.Post     阶段结束时
Event.Timing.Damage.Incoming            将要受到伤害
Event.Timing.Damage.Dealt               造成伤害时（对来源方的查询）
Event.Timing.Card.Move                  牌移动前（可干预）
Event.Timing.Card.AreaEnter             牌进入区域时
Event.Timing.Card.AreaLeave             牌离开区域时
Event.Timing.Dying                      濒死求桃
Event.Timing.PlayCard.Use               使用牌时（可被"无懈"类响应）

Event.Notify.Phase.Entered              阶段已进入（事实）
Event.Notify.Card.Moved                 牌已移动（事实）
Event.Notify.Damage.Applied             伤害已结算（事实）
Event.Notify.Damage.Prevented           伤害被防止（事实）
```

（标签常量已全部迁移为 5.x 原生 GameplayTag——`UE_DEFINE_GAMEPLAY_TAG`，声明即存在、不依赖 ini，见 4.4 与附录 C。）

### 4.3 响应窗口（ResponseWindow）

窗口由**服务器专用流程技能**持有，技能寿命 = 窗口寿命：

```cpp
// 窗口描述
struct FResponseWindow
{
    FGameplayTag TimingTag;              // 本次窗口对应的时机
    TObjectPtr<UBattleTransaction> Tx;   // 关联的交易（可空：纯阶段时机）
    TArray<FResponderEntry> Responders;  // 合法响应者名单（技能实例+所属玩家）
    float Timeout;                       // 超时兜底（秒）
};
```

规则细节：

- **单响应还是多响应**由时机决定：`Damage.Incoming` 允许多个技能依次响应；"是否打出无懈"是逐人询问。窗口配置里加一个 `EWindowPolicy`（AllAtOnce / InOrder / FirstOnly）。
- **询问顺序**：按当前回合玩家起逆时针/顺时针（规则表可配），由流程侧控制逐个激活，而不是依赖 `HandleGameplayEvent` 一次性唤醒全部。
- **超时**：`UAbilityTask_WaitDelay` 兜底，超时视为放弃响应。
- **窗口期上锁**：开窗时给相关玩家挂带 `State.Responding` 阻断标签的 GE，屏蔽无关技能与出牌。

### 4.4 标签的存在性（引擎结论存档）

**原生标签声明即存在。** `FNativeGameplayTag` 构造时直接向标签管理器注册（`NativeGameplayTags.cpp`），`UGameplayTagsManager::ConstructGameplayTagTree` 有独立工序收录原生标签——不经过 ini、不经过编辑器、不依赖模块与管理器的初始化顺序。本项目所有静态标签（`ArkWarTags.cpp` / `ArkWarFlowTypes.cpp`）均为此形态。

**`RequestGameplayTag` 只查不造。** 5.4 中查无此标签时返回无效标签（并 ensure），引擎原话：*"tags must be loaded from config or registered as a native tag"*。标签是封闭集合，运行期没有合法的造标签手段（`FGameplayTag` 构造函数私有，仅管理器与原生标签可用）。

**匹配不依赖注册。** `HasTag` / `MatchesTag` 是纯名字比较；注册只影响查找构造、编辑器标签选择器与复制索引效率。问题只出在"出生"一刻，不出在相处之中。

数据驱动标签的两条合规出路：

1. **有限常量集**（卡种类、技能区域名）→ 升为原生标签，一行一个；
2. **策划维护的开放集** → 单个 GameplayTags 数据资产（GameplayTag List Asset），一次性在 `DefaultGameplayTags.ini` 挂引用，此后只在资产内增删。

## 5. 交易家族（结算的载体）

### 5.1 基类生命周期

```cpp
UCLASS(Abstract)
class UBattleTransaction : public UObject
{
    GENERATED_BODY()
public:
    enum class EState : uint8 { Created, Querying, Executed, Finished };

    TObjectPtr<APlayerState> Instigator;   // 发起者
    TObjectPtr<APlayerState> Target;       // 目标（可空）

    void Begin();            // 填字段 → 推入流程的交易队列
    void QueryTimings();     // 逐个开查询时机窗口（异步，可被修改/取消）
    virtual void Execute() PURE;   // 同步落子：真正修改状态
    void NotifyTimings();    // 事实通知（同步广播 + 复制已生效）
    void Cancel();           // 被防止/无效化时调用

    // 窗口关闭后由流程回调，驱动生命周期前进
    void OnWindowClosed(const FResponseWindow& Window);
};
```

**"伤害悬置"的本质**：`Execute()` 还没有被调用。不需要暂停任何任务或函数，交易对象本身就是那个停泊点。

### 5.2 成员设计

| 交易 | 关键字段 | 查询时机 | 执行动作 |
|---|---|---|---|
| `UCardMoveTransaction` | `FMoveMessage` 解析结果：From/To/Num/Predicate/Order | `Card.Move`（可改数量/去向/取消） | 容器 `MoveIn/MoveOut` |
| `UDamageTransaction` | DamageType、Amount、bIgnored | `Damage.Incoming` / `Damage.Dealt` | 对目标 ASC 应用 SetByCaller 伤害 GE |
| `UDyingTransaction`（后续） | 濒死目标、已求桃数 | `Dying` | 救回或淘汰结算 |

### 5.3 嵌套与排队

- 交易进入**队列**执行，不直接递归：窗口响应中产生的新交易（如响应技能造成新伤害）入队，当前交易结算完毕后出队。
- 唯一允许插队的是规则指定的嵌套（如濒死结算打断当前流程），用显式栈管理，不做隐式递归。

## 6. 伤害结算全链路（参考实现）

以"杀命中 → 目标技能：摸一张牌并判定，红桃则无视本次伤害"为例：

```
 1. 攻击方出牌结算 → 流程创建 UDamageTransaction{来源, 目标, 数量}
 2. 广播查询时机 Event.Timing.Damage.Incoming（携带交易引用：
    FGameplayEventData::OptionalObject = Tx）
 3. SkillManager 按时机索引找到目标的监听技能 → 询问玩家是否发动
 4. 玩家发动 → 激活技能体 UAbility_HeartGuard（ServerOnly）
 5. 技能内部（AbilityTask 串联）：
      a. 摸一张牌（CardMoveTransaction：NUM=1 FROM=-AP TO=-AH）
      b. 判定：牌堆顶亮出 → 读取花色 Tag → 判定牌移入弃牌堆
      c. 花色 == Card.Suit.Heart → Tx->bIgnored = true
      d. Tx->NotifyResponded(this) → EndAbility
 6. 窗口关闭 → Tx->Resolve()
      bIgnored == true  → Cancel()，广播 Event.Notify.Damage.Prevented
      bIgnored == false → Execute()：构造 FGameplayEffectSpec，
                          SetSetByCallerMagnitude(数量)，
                          ApplyGameplayEffectSpecToSelf 扣血
 7. 广播 Event.Notify.Damage.Applied → 检查是否濒死（可能产生新交易）
```

技能体声明要点：

```cpp
// UAbility_HeartGuard
// NetExecutionPolicy = ServerOnly        窗口只由服务器裁决
// InstancingPolicy  = InstancedPerActor  允许并发实例
// 触发方式二选一：
//   A. AbilityTriggers + HandleGameplayEvent（适合全自动被动技）
//   B. 流程侧显式 TryActivateAbility（适合需要"询问是否发动"的技能，推荐）
```

## 7. 卡牌移动设计

卡牌移动是全游戏最高频的结算（摸牌、出牌、弃牌、判定、装备），从第一天就交易化：

1. **意图**：`FMoveMessage` 的 Msg 字符串解析为移动意图（现有 `CardMsgDef` 的 DSL 保留，作为交易的输入描述）。
2. **交易**：`UCardMoveTransaction` 承载意图，开 `Event.Timing.Card.Move` 窗口（多数移动无人响应，窗口空转即过，成本可忽略）。
3. **执行**：服务器侧经 `ICardContainerInterface::MoveOut/MoveIn` 修改 `UCardManagementBusComponent` 的区域状态。
4. **通知**：区域属性复制驱动客户端；广播 `Event.Notify.Card.Moved`，其中按去向/来源细分为 `AreaEnter/AreaLeave` 时机供技能监听（装备入场类技能的挂载点）。
5. **缓冲堆**（`-AU` / Used）：出牌阶段结束后的批量移动不触发弃牌事件——在交易的 Tag 上标注 `bConsiderAsDiscard`（字段已存在于 `FMoveMessage`），由时机层据此过滤。

## 8. 技能系统对接

技能 = **声明**（数据） + **技能体**（GAS Ability）：

```cpp
// FSkillInfo 增加声明字段
UPROPERTY(EditAnywhere)
FGameplayTagContainer ListenTimings;   // 监听的时机点标签集合
UPROPERTY(EditAnywhere)
TSubclassOf<UGameplayAbility> AbilityBody;  // 技能体
UPROPERTY(EditAnywhere)
int32 ResponsePriority = 0;            // 同一时机多技能时的响应顺序
```

- `USkillComponentBase`（挂在 PlayerState）持有当局技能实例，战斗开始时把技能体 Grant 给该玩家的 ASC。
- `USkillManagerSubsystem` 在注册技能时同步建立 **时机 → 技能列表** 的索引，开窗时直接查表，不做全量遍历。
- `ESkillActivateType` 与触发方式的对应：
  - **被动技/锁定技**：时机到达自动激活（锁定技不询问、不可放弃）。
  - **主动技**：玩家输入（ServerRPC）触发，流程校验合法性。
  - **限定技**：技能体自带 Cooldown GE 记次。
  - **策略技/指挥技**：按现有定义走主动触发通道。

## 9. 网络与客户端

- 客户端**没有任何流程任务**。它的世界由三类输入驱动：复制属性（阶段、区域、手牌、血量）、事实通知委托、GameplayCue（瞬时表现）。
- 客户端表现队列：收到的表现请求（卡牌飞行、判定翻牌、伤害数字）入本地队列顺序播放。队列慢于服务器不阻塞规则，快于服务器则等待数据到达。
- 玩家响应：窗口内的选择（发动/放弃、选目标、选牌）经 ServerRPC 提交，服务器校验"该玩家此刻是否有权响应"。
- 现有可复用件：`FPlayerSelectionChangeDelegate` / `FCardSelectionChangeDelegate` 留在客户端做选牌交互，不上行。

## 10. GameplayTask 使用边界（结论存档）

| 场景 | 用什么 |
|---|---|
| 阶段主轴（回合状态机） | 不用。同步 FSM |
| 响应窗口等待（含超时） | 用。流程技能内的自定义 AbilityTask |
| 技能内部多步等待（摸牌→判定→分支） | 用。AbilityTask 串联 |
| 交易状态（数值、目标、是否防止） | 不用。状态放交易对象，任务只管等 |
| 客户端阶段表现 | 不用。复制 + RepNotify |

备注：流程在技能内 → 用 AbilityTask；流程在技能外（纯子系统驱动）→ 裸 `UGameplayTask` + `UGameplayTasksComponent`。两者都不复制到客户端。

## 附录 D：资产字段挂接原则（已实施）

原则：**一对一的资产进原表，一对多的资产挂在宿主行上；只有新实体或多对多才开新表。**

| 资产 | 位置 | 形态 |
|---|---|---|
| 手牌卡面贴图 | `FHandCardInfo::CardTexture` | `TSoftObjectPtr<UTexture2D>`（软引用，按需加载） |
| 角色卡面贴图 | `FOperatorCardInfo::CardTexture` | `TSoftObjectPtr<UTexture2D>` |
| 角色语音 | `FOperatorCardInfo::VoiceLines` | `TMap<FGameplayTag, TSoftObjectPtr<USoundBase>>` |

语音键的约定：

- 通用时机用 `Voice.Event.*` 原生标签（`VoiceTags`：Select / CardPlay / Damage / Dying / Death / Victory）。
- 技能语音直接用对应技能标签作键。
- 语音资产一律软引用，播放前再加载；牌局内存不背音频的债。

既有数据表（`.uasset`）重新保存后即长出新列；语音无需新表。
